# gw — гейтвар ПЛИС

Всё на SystemVerilog. Ядра пишутся в подмножестве, которое одинаково читают Verilator, Yosys и
Gowin EDA: `logic`, `always_ff`/`always_comb`, параметры, без interface и package.

| Папка | Что |
|---|---|
| [`cores/`](cores/) | Платформонезависимые ядра: приём TPIU, метки времени, пакетизатор, SWD/JTAG, CSR, мосты к USB-чипу (HSPI для CH569, UHSIF для CH32H417) за общим интерфейсом потоков |
| [`platform/`](platform/) | Платформенный слой Gowin; пока только поведенческие модели примитивов (rPLL, ODDR, IOBUF) для Verilator |
| [`boards/`](boards/) | Верхние модули плат: [Tang Nano 20K, шаг 0](boards/tangnano20k/) — самотест в CH569 по HSPI 16 бит и замер CRC; [Tang Nano 9K](boards/tangnano9k/) — источник трассы, PPS и меандра для стенда; дальше зонд B, SLogic16U3 |
| [`test/`](test/) | Тестбенчи Verilator на C++, модели внешних микросхем |

```sh
make -C gw lint     # verilator --lint-only -Wall
make -C gw test     # все тестбенчи
make -C gw synth    # yosys synth_gowin, отчёт о ресурсах в gw/build/synth/
make -C gw board-synth                               # Tang Nano 20K, шаг 0
make -C gw board-pnr OSS=~/.local/opt/oss-cad-suite/bin/   # битстрим (nextpnr-himbaechel)
make -C gw board-gowin                               # то же в Gowin EDA (Windows, из WSL)
```

Нужны Verilator 5 и Yosys с `synth_gowin`. Локально — Verilator 5.034 и Yosys 0.51, в CI — пакеты
Ubuntu 24.04.

## Ядра

| Ядро | Что делает |
|---|---|
| [`tpiu_align`](cores/tpiu_align.sv) | Выравнивание сырого потока по полному синхрослову 0x7FFFFFFF: все 32 сдвига по биту за такт, поэтому годится для порта 1, 2 и 4 бита. Дальше — полуслова |
| [`tpiu_deframer`](cores/tpiu_deframer.sv) | Автомат ПОИСК → ПРОВЕРКА → ЗАХВАТ ([`hw/img/fsm.svg`](../hw/img/fsm.svg)), кадры по 16 байт с 64-битным номером, вырезка синхрослов и полусинхрослов |
| [`tpiu_idle`](cores/tpiu_idle.sv) | Выброс пустых кадров: все данные под ID 0, и кадр не меняет текущий ID |
| [`tpiu_rx`](cores/tpiu_rx.sv) | Цепочка из трёх ядер выше |
| [`trace_capture`](cores/trace_capture.sv) | Домен TRC_CLK: две выборки IDDR за такт (порядок «подъём/спад» настраивается) → 32-битные слова для порта 1, 2 и 4 бита |
| [`async_fifo`](cores/async_fifo.sv) | Асинхронный FIFO, указатели в коде Грея |
| [`trace_rx`](cores/trace_rx.sv) | Весь приём трассы через оба домена: захват → FIFO → `tpiu_rx`; слова, не влезшие в FIFO, считаются (счётчик в коде Грея) |
| [`selftest_gen`](cores/selftest_gen.sv) | Генератор потока самотеста в формате [`stream.h`](../fw/ch569/usbstream/stream.h): нагрузка `stream_word(k)` или PRBS31, проверяется на ПК тем же `sw/usbstream` |
| [`hspi_tx`](cores/hspi_tx.sv) | Передатчик HSPI в CH569 на 8/16/32 бита: запрос и готовность, заголовок с номером пакета и полем пользователя, CRC16/CRC32 с настраиваемыми параметрами. Протокол — [`doc/ch569-hspi.md`](../doc/ch569-hspi.md) |
| [`uart_tx`](cores/uart_tx.sv), [`uart_hex`](cores/uart_hex.sv) | UART 8N1 и выгрузка пакетов `hspi_rx` hex-строками для `find_crc.py` |
| [`uart_status`](cores/uart_status.sv), [`uart_mux`](cores/uart_mux.sv) | Строка состояния hex-словами; две строки в один UART по очереди, целиком |
| [`tpiu_tx`](cores/tpiu_tx.sv) | Синтетический порт трассы TPIU: кадры, вычисляемые по номеру, синхрослова, 4/2/1 бит, DDR-выборки (Tang Nano 9K, шаг 2) |
| [`selftest_hspi`](cores/selftest_hspi.sv) | Генератор и передатчик вместе, блок на пакет: ПЛИС-часть шага 0 |
| [`hspi_rx`](cores/hspi_rx.sv) | Приём HSPI от CH569 (команды) на такте HTCLK: HTRDY только при месте под целый пакет, CRC отделяется линией задержки, признак «пакет хороший» на закрывающем слове; сырой режим для замера CRC. FIFO в один блок BSRAM |

Приём TPIU разбирает поток по полусловам: кадр — 8 полуслов, полное синхрослово 0xFFFF 0x7FFF,
полусинхрослово 0x7FFF. Чётный байт кадра не бывает 0xFF (это смена ID на зарезервированный 0x7F),
поэтому 0xFFFF внутри кадра не встречается и задерживается на одно полуслово: если за ним 0x7FFF, это
полное синхрослово. Пропускная способность — одно 32-битное слово за два такта, то есть 2 байта за такт: 200 МБ/с при
100 МГц против 84 МБ/с пика STM32F407.

Ресурсы по `synth_gowin`: `tpiu_rx` — около 1250 LUT и 300 ALU (почти всё — 64-битный номер кадра и
32-битные счётчики), `selftest_hspi` на 16 бит — около 500 LUT и 230 ALU. Вместе около 10 % GW2AR-18.

Мост к USB-чипу сменный: ядра выше него видят только потоки (трасса, события, ответы, команды) с
готовностью и признаком конца пакета. Под ними — HSPI (CH569) или UHSIF в режиме «ведомый для ПЛИС»
(CH32H417, синхронный FIFO с флагами WRNF/AF#/RDNE/AE#). Выбор между ними — по шагу 0 плана проверки.

## Тесты

[`test/tpiu/tb_tpiu.cpp`](test/tpiu/tb_tpiu.cpp) строит поток TPIU из случайных корректных кадров и
задаёт ожидаемый выход явно для каждого сценария: все 32 сдвига по биту, полусинхрослова между кадрами
и внутри них, синхрослово не на границе кадра, неудачная ПРОВЕРКА, проскальзывание бита с таймаутом
и повторным захватом, пустые кадры. Вход и выход случайно приостанавливаются.

[`test/trace/tb_trace.cpp`](test/trace/tb_trace.cpp) гоняет `trace_rx` с двумя независимыми тактами:
порт 1, 2 и 4 бита, оба порядка выборок, разные соотношения TRACECLK и sys, худший случай STM32F407
(4 бита, 84 МГц, 3000 кадров без потерь), переполнение FIFO при слишком медленном sys. При неверном
порядке выборок нибблы в байте переставлены, и два синхрослова подряд всё равно дают 31 единицу и ноль
на сдвинутой позиции: деформатор может захватить синхронизацию, но правильных кадров не будет.
Признак неверного порядка — захват есть, а кадры не декодируются.

[`test/hspi/tb_hspi.cpp`](test/hspi/tb_hspi.cpp) соединяет `selftest_hspi` с моделью приёмника CH569
([`test/models/ch569_hspi.h`](test/models/ch569_hspi.h)): два буфера DMA, задержка ответа, случайное
время разгрузки буфера. Принятые данные идут в `sw/usbstream/check.c`. Собирается четыре раза: шина 8,
16, 32 бита и 16 бит с отражённым CRC (начало и XOR 0xFFFF). Сценарии: полная скорость (загрузка шины
98,7–99,6 % при блоках 4096 байт), медленный приёмник без потерь, сбой бита на шине (пакет отбрасывается
по CRC, на ПК — потерянный блок), порча после проверки CRC (на ПК — испорченный блок). CRC модели
сверяется с контрольными значениями каталога CRC.

[`test/hspi/tb_hspi_rx.cpp`](test/hspi/tb_hspi_rx.cpp) — обратное направление: модель передатчика CH569
([`test/models/ch569_hspi_tx.h`](test/models/ch569_hspi_tx.h): HTREQ, ожидание HTRDY, 10+ тактов на
FIFO, провалы HTVLD) на своём такте против `hspi_rx`. Пакеты случайной длины при разных соотношениях
тактов, долгая остановка потребителя (HTRDY держит передатчик, потерь нет), сбой бита, пропуск номера,
TLL2B ≠ 0, слишком длинный пакет — плохим помечается только он; сырой режим. Те же четыре сборки по
ширине и CRC. `make crc-check` — репетиция замера CRC на шаге 0.

[`test/loop/tb_loop.cpp`](test/loop/tb_loop.cpp) — петля `tpiu_tx` → `trace_rx` на разных тактах: порт 1,
2, 4 бита, синхрослова каждый кадр и раз в 64 кадра, с полусинхрословами; каждый принятый кадр должен
совпасть с кадром своего номера. [`test/uart/tb_uart.cpp`](test/uart/tb_uart.cpp) — пакеты и строки
состояния через `uart_mux` в линию UART и обратно в текст: строки целые, пакеты по порядку.

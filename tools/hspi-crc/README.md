# hspi-crc — параметры CRC HSPI CH569 по пакетам с шины

В даташите CH569 есть только полиномы CRC HSPI. [`find_crc.py`](find_crc.py) подбирает остальное по
настоящим пакетам: ширину, что покрыто (заголовок и данные или только данные), отражение на входе и
выходе, порядок байт CRC на шине, начальное значение (все 65536 для CRC16, 0 и все единицы для CRC32) и
выходной XOR. CRC линеен по начальному значению, поэтому полный перебор занимает около секунды.

```sh
python3 tools/hspi-crc/find_crc.py --selftest
python3 tools/hspi-crc/find_crc.py packets.txt     # пакет на строку, hex
```

Нужны пакеты хотя бы двух разных длин, иначе начальное значение и выходной XOR не разделить. Для CRC16
с полиномом 0x8005 (он делится на x+1) при длинах, кратных 4 байтам, остаётся пара равносильных
решений — например, init 0xFFFF / xorout 0xFFFF и init 0x7FFC / xorout 0x3FFE. Для наших пакетов (данные
целыми словами) обе дают один и тот же CRC.

На стенде (шаг 0): CH569 шлёт в ПЛИС пакеты известной длины, `gw/cores/hspi_rx.sv` с `cfg_raw = 1`
отдаёт их целиком вместе с CRC, пакеты выгружаются на ПК — сюда. Найденные значения идут в параметры
`CRC_INIT`, `CRC_REFLECT`, `CRC_XOROUT` у `hspi_tx` и `hspi_rx`. Если `CRC_REFLECT` разный на входе и
выходе, параметров RTL не хватит — тогда их надо разделить.

Репетиция в симуляции: `make -C gw crc-check` — модель CH569 шлёт пакеты с CRC16 (init и XOR 0xFFFF,
с отражением), `hspi_rx` в сыром режиме, `find_crc.py` должен найти именно эти параметры.

# tools/slogic/pinmap — прозвонка выводов SLogic16U3

Схемы прибора нет. Образ `pinmap.bin` ищет, на какие выводы GW5AT-15 (корпус CS130) приходят каналы
гребёнки. Наружу он ничего не выдаёт, кроме линий SPI к своей флеш, поэтому неизвестная разводка не
страдает: все свободные выводы — входы.

> **Статус на 2026-10-21: опыт прерван, прибор не возвращается в DFU.** Образ записан и загрузился, но
> кнопка MODE больше не даёт DFU, USB2 не поднимается. Отчёт не прочитан. Подробности и план
> восстановления — [ниже](#опыт-2026-10-21).

## Как устроено

| Часть | Файл | Что делает |
|---|---|---|
| Гейтвар | [`pinmap.v`](pinmap.v), [`pinmap.cst`](pinmap.cst) | 40 входов `p[i]` с подтяжкой вверх. Такт — внутренний OSCB, 210/4 = 52,5 МГц. Пауза 2^25 тактов (0,6 с), затем окно 2^28 тактов (5,1 с): на каждом входе считаются фронты, отмечается, был ли 0 и 1. Потом отчёт пишется во флеш по 0x7F0000 |
| Сборка | [`gowin.tcl`](gowin.tcl) | `gw_sh gowin.tcl` в копии папки (Gowin EDA 1.9.12.04, Windows). `-use_{mspi,sspi,cpu,i2c}_as_gpio`, multiboot на 0x800000. Готовый образ — `pinmap.bin` (открытый, синхрослово A5C3) |
| Симуляция | [`tb.v`](tb.v) | Модель SPI-флеш: последовательность команд, адреса, страница отчёта. `iverilog -g2012 -o tb tb.v pinmap.v && vvp tb` |
| Источник | [`stm32/`](stm32/) | STM32F4-Discovery, 18 линий меандра с известными частотами |
| Разбор | [`pinmap.py`](pinmap.py) | Читает страницу 0x7F0000 в DFU (или из файла: `--file`), сопоставляет выводы с каналами |

### Выводы GW5AT-15 CS130

Таблица выводов взята из Gowin EDA: `IDE/data/device/GW5AT-15B/CS130.json`. В корпусе 53 вывода
общего назначения, остальное — SerDes (Q0_*), MIPI (M0_*, M1_*) и питание.

| Группа | Шарики | В образе |
|---|---|---|
| JTAG | E8 TCK, E7 TMS, H8 TDI, H7 TDO | не тронуты: путь восстановления |
| RECONFIG_N | K6 | не тронут: на нём кнопка MODE |
| DONE, READY, MODE0/1 | K7, K5, H6, G6 | не тронуты |
| MSPI к флеш | H4 MCS_N, H5 CCLK, K4 MOSI (D00), G4 MISO (D01) | SPI-мастер образа |
| D02, D03 | G5, J4 | входы с подтяжкой: это IO2/IO3 флеш, если она в quad |
| Остальные 38 | D2 D3 D4 E1–E4 F1–F5 F7 F8 G1–G3 H1–H3 J1–J3 J7 J8 K1–K3 L1–L4 M1–M3 N1–N3 | входы `p[i]`, порядок — в `pinmap.cst` |

Флеш — XTX, JEDEC `0b4018`, команды стандартные: 06, 20, 02, 05, 9F; перед ними FF×4 (выход из
continuous read) и 66/99 (сброс).

### Отчёт во флеш

Страница 256 байт по 0x7F0000, стирается только сектор 0x7F0000–0x7F0FFF. Пишет образ, только если
JEDEC ID совпал. `write` и `restore` утилиты эту область стирают вместе со всей основной.

| Смещение | Что |
|---|---|
| 0 | `RLNP` |
| 4 | версия (1) |
| 5 | число выводов (40) |
| 6–8 | JEDEC ID |
| 9 | log2 длины окна в тактах (28) |
| 16 + 4i | вывод `p[i]`, u32 LE: [31] был 1, [30] был 0, [29] уровень в конце окна, [28:0] фронтов |

### Источник на STM32F4-Discovery

Счётчик `n` на выводах: бит k (канал CHk) переключается 500 кГц / 2^k раз в секунду
(HSI 16 МГц, шаг 32 такта по SysTick). Канал опознаётся по log2(ожидаемое / измеренное), частота
внутреннего генератора ПЛИС (±несколько %) на это почти не влияет.

| Каналы | Выводы STM32 |
|---|---|
| CH0–CH7 | PD0–PD7 |
| CH8–CH15 | PE0–PE7; биты 8 и 9 продублированы на PE8, PE9 |

```sh
make -C tools/slogic/pinmap/stm32
openocd -f board/stm32f4discovery.cfg -c "program tools/slogic/pinmap/stm32/pattern.elf verify reset exit"
```

Что выяснилось на этой плате:

- **PE0 и PE1 держит акселерометр** (INT1/INT2). Прошивка проверяет это подтяжками вверх и вниз;
  если вывод не идёт за подтяжкой, он остаётся входом, горит красный PD14. Так и вышло: CH8 и CH9
  нужно брать с PE8 и PE9. Зелёный PD12 мигает ~1 Гц — прошивка работает.
- **ST-LINK/V2 на Discovery со старой прошивкой V2J14**: pyOCD с ней не работает (нужна V2J24+),
  OpenOCD из OSS CAD Suite — работает. Тулчейн: xPack arm-none-eabi-gcc 15.2.1 в `~/.local/opt`.
- **Отладчик при подключении сбрасывает DWT**, и цикл по `CYCCNT` встаёт. Поэтому шаг отмеряет SysTick.

| Шаг | Что было |
|---|---|
| `write pinmap.bin` | записано и сверено 491 882 байт с 0x0 |
| Переподключение | Windows: «сбой запроса дескриптора», `0000:0002`, `CM_PROB_FAILED_POST_START`. С пустым образом `probe/` устройства не было вовсе |
| Индикатор | синий горит, красный мигает ~1 Гц (виден фиолетовым). С `probe/` горел только синий. Пока MODE нажата — красный |
| MODE | DFU (`359f:30f1`) не появляется. Перезапуск устройства в Windows, переподключение — тоже нет |

Отчёт не прочитан, состояние флеш неизвестно.

### Версии

1. **Подтяжки 40 выводов мешают USB-части платы.** С пустым образом незанятые выводы оставались в
   состоянии Gowin по умолчанию, здесь все 40 явно подтянуты вверх. Похоже, один из них включает
   подтяжку D+ или будит USB2-PHY: хост видит подключение, но ответа нет. Почему после MODE не
   поднимается и DFU, не объяснено: подтяжки переживают реконфигурацию, но золотой образ должен бы
   задать свои уровни. Мигание красным ~1 Гц похоже на узор DFU, то есть золотой образ, вероятно,
   работает.
2. **Повреждена золотая область 0x800000.** По построению образа маловероятно: обе записывающие
   команды (0x20 и 0x02) имеют константный адрес 0x7F0000, запись только после правильного JEDEC ID,
   в симуляции одно стирание и одна запись. Но на железе SPI-мастер на CCLK не проверялся: сдвиг
   битов в команде дал бы другую команду с другим адресом. Исключить это может только чтение флеш.

### Восстановление (следующий шаг)

Вскрыть прибор и читать флеш напрямую через FT2232H, канал A в режиме MPSSE. Утилита та же, с ключом
`--ftdi` (нужен pyftdi):

| FT2232H | Флеш (SOP-8/WSON-8) |
|---|---|
| ADBUS0 | CLK (6) |
| ADBUS1 | DI / IO0 (5) |
| ADBUS2 | DO / IO1 (2) |
| ADBUS3 | CS# (1) |
| GND | GND (4) |

Прибор питается своим USB, MODE (RECONFIG_N) прижат к земле, чтобы ПЛИС не выходила на шину.
Цоколёвку сверить по фото платы (корпус флеш не известен), заодно найти площадки JTAG ПЛИС и
микросхему USB у разъёма.

```sh
uv run --with pyftdi python3 tools/slogic/slogic_dfu.py --ftdi ftdi://ftdi:2232h/1 id
uv run --with pyftdi python3 tools/slogic/slogic_dfu.py --ftdi ftdi://ftdi:2232h/1 dump after-pinmap.bin
cmp -l after-pinmap.bin slogic16u3-factory.bin | head     # где расходится с бэкапом
python3 tools/slogic/pinmap/pinmap.py --file <(tail -c +$((0x7F0000 + 1)) after-pinmap.bin | head -c 256)
uv run --with pyftdi python3 tools/slogic/slogic_dfu.py --ftdi ftdi://ftdi:2232h/1 restore slogic16u3-factory.bin
```

1. `id` — JEDEC `0b4018`. Если `ffffff` или `000000`, ПЛИС держит шину или неверна проводка.
2. Дамп и сравнение с бэкапом. Ожидаемо расходятся 0x0–0x7FFFF (`pinmap.bin` вместо приложения) и
   0x7F0000–0x7F00FF (отчёт). Всё остальное, особенно 0x800000 и выше, должно совпасть.
3. Если в 0x7F0000 есть `RLNP` — разобрать отчёт: результат прозвонки получен.
4. `restore`: заводское приложение в 0x0. При включении грузится 0x0, поэтому прибор вернётся,
   даже если с DFU что-то не так. `restore` проверяет золотой образ во флеш по бэкапу и при
   расхождении откажется. Тогда сначала нужно чинить 0x800000 из бэкапа — такой команды в утилите
   пока нет, специально.

`--ftdi` написан, но на железе ещё не запускался.

### Что поменять в следующей прозвонке

- Не подтягивать все выводы вверх. Сначала найти USB-линии и индикатор (их сейчас видно как
  0000:0002 и синий/красный), оставить остальные в состоянии по умолчанию или с подтяжкой вниз.
  Сравнить с поведением пустого `probe/`, где DFU по MODE работал.
- Перед записью своего образа убедиться, что есть путь восстановления без DFU (JTAG или флеш
  напрямую). Сейчас его не было.

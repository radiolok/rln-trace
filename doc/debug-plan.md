# План: отладочная часть зонда (JTAG, SWD, SWO, cJTAG)

Трасса уже работает (SLogic16U3: STM32F407 и BE-U1000 через USB 3.0, см. [README](../README.md#статус)).
Этот документ — план второй половины зонда: всего, что на MIPI20 идёт **в цель**, а не из неё.
Он расписывает шаги 6 и 7 [плана проверки](../hw/README.md#9-план-проверки) и требование R5.

## 1. Что нужно в итоге

Полный набор функций разъёма MIPI20:

| Интерфейс | Линии MIPI20 | Сложность | Где основная работа |
|---|---|---|---|
| JTAG (IEEE 1149.1) | TCK, TMS, TDI, TDO, nRESET | низкая | сдвиговый движок, остальное делает хост |
| SWD | SWCLK, SWDIO, nRESET | низкая–средняя | разворот шины, ACK WAIT/FAULT, чётность |
| SWO | TDO/SWO | средняя | приём NRZ и Manchester, частота, поток на ПК |
| cJTAG (IEEE 1149.7, OScan1) | TCKC = TCK, TMSC = TMS | высокая | активация и escape-последовательности, формат OScan1, мало поддержки в софте |
| Параллельная трасса | TRACECLK, TRACED0–3 | **готово** | — |

Вне рамок: RVSWD (WCH), Mictor-38, nTRST и RTCK (их нет на MIPI20; см. [hw/README.md § 6](../hw/README.md#6-отладка)).

### Матрица по реализациям

`rln-trace` — общая точка входа для нескольких зондов. Не каждая реализация обязана уметь всё:

| | Стенд Tang Nano 20K | Зонд B (GW2AR-18 + CH569) | SLogic16U3 + адаптер |
|---|---|---|---|
| Параллельная трасса 4 бита | ✅ | ✅ | ✅ (готово) |
| SWO (NRZ / Manchester) | ✅ (медленно, через UART) | ✅ | ✅ |
| PPS / триггеры | ✅ | ✅ | ✅ |
| JTAG / SWD | ✅ этапы D1–D3 | ✅ CMSIS-DAP v2 | ✅ через адаптер (этап D6) |
| cJTAG, Spy-Bi-Wire | ✅ этап D7 | ✅ этап D7 | по возможности |
| Нативный CMSIS-DAP на USB | ❌ (UART) | ✅ free-dap на CH569 | решение на этапе D6 |

Таблица попадёт и в главный README, когда этапы D3 и D6 будут закрыты.

## 2. Архитектура

```
 ПК                      мост (сменный)               ПЛИС (общие ядра)                    цель
┌─────────────┐   ┌───────────────────────┐   ┌────────────────────────────────┐   ┌────────┐
│ OpenOCD     │   │ UART BL616 (стенд)    │   │ dbg_cmd   ── разбор пакетов    │   │        │
│ pyOCD       │◄─►│ CH569: free-dap+HSPI  │◄─►│ dbg_shift ── сдвиговый движок  │◄─►│ MIPI20 │
│ probe-rs    │   │ SLogic: USB3 в ПЛИС   │   │ dbg_swd   ── транзакции SWD    │   │        │
│ sw/dbgprobe │   └───────────────────────┘   │ dbg_phy   ── выводы, OE, фаза  │   │        │
└─────────────┘                               │ swo_rx    ── приём SWO         │   └────────┘
                                              └────────────────────────────────┘
```

Главное решение: **ядра отладки видят только поток команд и поток ответов** (данные, готовность,
конец пакета) — тот же интерфейс, что у остальных ядер за мостом ([gw/README.md](../gw/README.md)).
Транспорт меняется, ядро — нет:

| Реализация | Транспорт команд | Кто разбирает CMSIS-DAP |
|---|---|---|
| Стенд Tang Nano 20K | UART BL616 (пакеты COBS + CRC8) | никто: на ПК `sw/dbgprobe` (Python) или OpenOCD remote_bitbang |
| Зонд B | HSPI CH569 ↔ ПЛИС, поле пользователя заголовка — тип потока | [free-dap](../au/free-dap) на CH569 |
| SLogic16U3 | своя пара конечных точек USB 3.0 в образе ПЛИС | решение на этапе D6 |

### Ядра (в `gw/cores/`, SystemVerilog в общем подмножестве)

| Ядро | Что делает |
|---|---|
| `uart_rx` | Приём UART 8N1 (пока в репозитории только `uart_tx`) |
| `cobs_rx`, `cobs_tx` | Кадры COBS с CRC8 поверх байтового потока — только для UART-транспорта |
| `rbb_uart` | Интерпретатор протокола OpenOCD remote_bitbang — этап D1, потом остаётся как отладочный режим |
| `dbg_cmd` | Разбор команд, очередь ответов, регистры настройки (делитель TCK, режим, задержка выборки) |
| `dbg_shift` | Универсальный сдвиговый движок по образцу MPSSE: N тактов, на каждом — TMS, TDI (или SWDIO), направление SWDIO, флаг захвата TDO/SWDIO |
| `dbg_swd` | Ускоритель транзакций SWD поверх `dbg_shift`: запрос → ACK → данные + чётность, повторы WAIT |
| `dbg_jtagdp` | Ускоритель DPACC/APACC через JTAG-DP (после D3, по замерам) |
| `dbg_phy` | Выводы: регистры у пинов, OE каждого буфера с настраиваемой полярностью, подстройка момента выборки TDO/SWDIO |
| `swo_rx` | Приём SWO: NRZ с передискретизацией и Manchester; выход — поток байтов ITM |
| `oscan1` | Мост 4-проводного JTAG в cJTAG OScan1 — этап D7 |
| `sbw` | Spy-Bi-Wire для MSP430 — этап D7 |

### Набор команд (черновик)

Точный формат фиксируется на этапе D2 в `doc/dbg-protocol.md`. Набор повторяет семантику CMSIS-DAP,
чтобы на CH569 команды DAP переводились в команды ПЛИС почти один к одному.

| Команда | Аналог CMSIS-DAP | Содержимое |
|---|---|---|
| `INFO` | `DAP_Info` | версия гейтвара, битовая маска возможностей (JTAG, SWD, SWO, OScan1, SBW), частота sys |
| `CFG` | `DAP_SWJ_Clock`, `DAP_SWD_Configure` | делитель TCK, режим линии, такты разворота, задержка выборки, полярность OE |
| `PINS` | `DAP_SWJ_Pins` | прямое чтение и запись nRESET, TCK, TMS, TDI; чтение TDO и VREF-ok |
| `SEQ` | `DAP_JTAG_Sequence`, `DAP_SWJ_Sequence`, `DAP_SWD_Sequence` | до 64 тактов: векторы TMS, TDI, направления, маска захвата → биты TDO |
| `SWD_XFER` | `DAP_Transfer` (SWD) | запрос, данные записи, число повторов WAIT → ACK и данные чтения |
| `JTAG_XFER` | `DAP_Transfer` (JTAG) | после этапа D3 |
| `SWO_CFG`, `SWO_CTRL` | `DAP_SWO_*` | режим NRZ/Manchester, делитель, старт и стоп |

Ответ каждой команды несёт её номер (тег): команды конвейеризуются, хост не ждёт ответа на каждую.

## 3. Этапы

Каждый этап заканчивается тестом в Verilator (`make -C gw test`) и проверкой на железе. Ход работ —
в журнале `doc/debug-journal.md` в том же стиле, что журналы трассы.

### D0. Стенд

**Цель:** Tang Nano 20K и F4-Discovery соединены, ничего не горит, OpenOCD с эталонными отладчиками работает.

- **F4-Discovery:** снять обе перемычки CN3 — встроенный ST-LINK отключается от SWD своего STM32F407.
  Перемычки хранить рядом: вернуть их — значит снова получить эталонный отладчик.
- **Отдельный верхний модуль `gw/boards/tangnano20k/top_dbg.sv`** и `tangnano20k_dbg.cst`: CH569 на этих
  этапах не нужен, выводы HSPI свободны. Предлагаемая раскладка (уточняется в `.cst`):

  | Сигнал | STM32F407 | Tang Nano 20K |
  |---|---|---|
  | TMS / SWDIO | PA13 | 20 |
  | TCK / SWCLK | PA14 | 19 |
  | nRESET | NRST | 18 |
  | TDI | PA15 | 73 |
  | TDO / SWO | PB3 | 74 |
  | nTRST | PB4 | 75 (только для опытов: на MIPI20 его нет) |
  | TRACECLK, TRACED0–3 | PE2–PE6 | 77; 15, 16, 27, 28 — как у трассы |
  | UART к ПК | — | 69 (TX), 70 (RX) — сверить по схеме платы |

  20, 19, 18 — те же выводы, что в плане шага 6; трасса и отладка работают одновременно.
- **Проводка:** 100–220 Ом последовательно на всех линиях от ПЛИС к цели (защита, пока гейтвар не отлажен),
  общая земля толстым проводом, провода до 15 см, земля рядом с TCK.
- **Уровни:** 3,3 В с обеих сторон, трансляторы на стенде не нужны.
- **Эталоны:** ST-LINK (перемычки CN3 на месте) и FT2232H канал B в режиме MPSSE (`interface/ftdi`,
  4-проводной JTAG) — оба должны прочитать IDCODE до начала работы с нашим движком.
- **UART BL616:** выяснить максимальную скорость, которую держит прошивка BL616 (цель — 2–3 Мбод;
  115200 тоже годится, только медленно). Записать в журнал.

**Готово, когда:** OpenOCD через FT2232H видит цепочку STM32F407 —
TAP Cortex-M4 `0x4BA00477` и boundary-scan `0x06413041`; ST-LINK по SWD видит SW-DP `0x2BA01477`.

### D1. JTAG через OpenOCD remote_bitbang

**Цель:** за минимум кода проверить проводку, уровни и цель, и сразу получить полный OpenOCD.

- `uart_rx` + `rbb_uart`: символы `0`–`7` выставляют TCK/TMS/TDI (бит 2 — TCK, бит 1 — TMS,
  бит 0 — TDI), `R` возвращает `0` или `1` по TDO, `r`/`s`/`t`/`u` управляют сбросами, `B`/`b`
  (светодиод) игнорируются. Протокол и полярность сбросов — по описанию remote_bitbang в документации
  OpenOCD; сверить по исходникам своей версии.
- В новых версиях OpenOCD у remote_bitbang есть расширение для SWD (управление и чтение SWDIO) —
  если оно есть в нашей версии, SWD можно проверить уже здесь.
- На ПК UART пробрасывается в TCP:

  ```sh
  socat TCP-LISTEN:3335,reuseaddr,fork FILE:/dev/ttyUSB1,b3000000,raw,echo=0
  openocd -c "adapter driver remote_bitbang; remote_bitbang host localhost; remote_bitbang port 3335" \
          -c "transport select jtag" -f target/stm32f4x.cfg
  ```

- **Тест Verilator:** `test/dbg/tb_rbb.cpp` с моделью TAP (`test/models/jtag_tap.h`: автомат 16 состояний,
  IR 4 бита, IDCODE, BYPASS, свой регистр данных произвольной длины). Тестбенч гоняет команды
  remote_bitbang через `uart_rx` и сверяет TDO и состояние TAP с моделью.

**Готово, когда:** OpenOCD читает оба IDCODE, `halt`/`resume`/`reg`, пишет тестовую прошивку
(`flash write_image erase ... ; verify_image`), GDB ставит точку останова и шагает. Скорость remote_bitbang
через UART записать в журнал — это нижняя планка для следующих этапов.

### D2. Сдвиговый движок и командный протокол

**Цель:** движок, который будет жить во всех реализациях; хост на Python поверх UART.

- `dbg_shift`: такт TCK из sys (96–120 МГц) делителем, от sys/2 до сотен кГц. На каждом такте —
  выставить TMS/TDI на спаде TCK, выбрать TDO на подъёме **плюс настраиваемая задержка** (в тактах sys,
  позже — IODELAY): компенсирует задержку линии туда и обратно, без неё на проводах частота упрётся
  в 5–10 МГц.
- `dbg_cmd` + `cobs_rx`/`cobs_tx`: команды `INFO`, `CFG`, `PINS`, `SEQ` из раздела 2; конвейер
  команд с тегами; ошибки CRC и переполнения считаются и видны в `INFO`.
- `dbg_phy`: регистры в IOB, OE для каждой линии (на стенде всегда включён, кроме SWDIO),
  Hi-Z по сбросу и до первой команды `CFG`.
- **Хост `sw/dbgprobe/` (Python):** транспорт (pyserial), API движка, автомат TAP, сканы IR/DR,
  ADIv5 через JTAG-DP (DPACC/APACC), MEM-AP (чтение и запись памяти, автоинкремент).
- **Тесты Verilator:** `test/dbg/tb_shift.cpp` — случайные последовательности против эталона на C++,
  все делители, все задержки выборки; `tb_cmd.cpp` — поток COBS с ошибками CRC и паузами.
- **Ресурсы:** записать LUT/FF для GW2AR-18 (`make -C gw synth`), как для остальных ядер.

**Готово, когда:** `dbgprobe` читает IDCODE, включает питание отладки (CTRL/STAT CSYSPWRUPACK/CDBGPWRUPACK),
читает `DBGMCU_IDCODE` по 0xE0042000 (DEV_ID 0x413), пишет и сверяет 64 КБ SRAM по 0x20000000.
Подбор максимального TCK на проводах и записанная зависимость «частота → нужная задержка выборки».

### D3. SWD

**Цель:** второй режим движка и ускоритель транзакций.

- Режим SWD в `dbg_shift`: SWDIO с направлением по маске, такты разворота (1–4), выборка по подъёму SWCLK.
- Последовательности через `SEQ`: сброс линии (≥ 50 единиц), JTAG→SWD (`0xE79E`), SWD→JTAG (`0xE73C`),
  выход из dormant (для целей с SWD v2 — запас на будущее, у STM32F407 SWD v1).
- `dbg_swd`: запрос (start, APnDP, RnW, A[2:3], чётность, stop, park) → разворот → ACK →
  данные и чётность; WAIT — повтор до заданного числа, FAULT — в ответ, ошибка чётности — отдельный код.
- **Модель SW-DP** (`test/models/swd_dp.h`): ACK OK/WAIT/FAULT по сценарию, проверка чётности,
  регистры DP, простой MEM-AP поверх памяти модели.
- **Сверка с эталоном:** SLogic16U3 щупами на SWDIO/SWCLK, декодер sigrok `swd` — транзакции нашего
  движка рядом с ST-LINK.

**Готово, когда:** через `dbgprobe` в режиме SWD — IDCODE `0x2BA01477`, те же тесты памяти, что в D2;
FAULT вызывается намеренно (доступ к несуществующему адресу) и правильно сбрасывается через ABORT;
переход JTAG↔SWD без передёргивания питания.

### D4. SWO

**Цель:** приём SWO — у всех реализаций, включая SLogic.

- `swo_rx`, режим NRZ: передискретизация ×8–16, скорость задаётся делителем; автоопределение скорости
  по ширине самого короткого импульса — по желанию.
- Режим Manchester: восстановление такта по фронтам, оценка полупериода по первому биту пакета.
- Выход — поток байтов ITM в отдельный поток моста (свой тег), не смешивается с трассой TPIU.
- На стенде: SWO на медленной скорости (сотни кБод), чтобы влезть в UART до ПК вместе с командами.
- Сверка: те же данные ITM через ST-LINK (OpenOCD `tpiu config internal ... uart off ...`) и через наш приём.

**Готово, когда:** printf через ITM и выборка PC (DWT) приходят в Orbuculum из файла или сокета;
NRZ и Manchester на нескольких скоростях; ошибки кадра считаются.

### D5. Перенос на CH569 (зонд B, стенд шага 0)

**Цель:** настоящий отладчик CMSIS-DAP v2, с которым работает обычный софт.

- [free-dap](../au/free-dap) на CH569: команды DAP переводятся в команды ПЛИС, ответы приходят по
  HSPI ПЛИС → CH569. Поток команд — CH569 → ПЛИС через `hspi_rx` (уже есть и проверено в тестах).
- USB составной: CMSIS-DAP v2 (vendor class, строка интерфейса «CMSIS-DAP»), трасса, события — как в
  [hw/README.md § 7](../hw/README.md#7-usb-интерфейсы).
- Пока CH569 на проводках, UART-транспорт остаётся как запасной путь отладки ядра.

**Готово, когда:** OpenOCD (`adapter driver cmsis-dap`), pyOCD и probe-rs видят зонд, шьют STM32F407
и останавливают ядро; openFPGALoader через CMSIS-DAP шьёт Tang Nano 9K по JTAG (JTAG-цель не ARM,
шаг 7 плана проверки). Записать скорость чтения памяти и прошивки против ST-LINK и FT2232H.

### D6. SLogic16U3: адаптер и отладка

**Цель:** JTAG/SWD через свой адаптер к SLogic: MIPI20, буферы 74xx126, 22 Ом.

Проверить на схеме адаптера до заказа плат:

- [ ] **Порог буфера против уровня на гребёнке.** Выход ПЛИС проходит через входной делитель SLogic
      (~0,47) и на гребёнке даёт около 1,2 В. У 74LVC126 с питанием 3,3 В VIH = 2,0 В — такой уровень
      он не примет. Нужен буфер с низким порогом на стороне ПЛИС: двухпитательный транслятор
      (SN74AXC1T45/2T45: сторона A от 1,2 В, сторона B от VREF), «анти-делитель» или компаратор.
- [ ] **OE при неконфигурированной ПЛИС.** OE у 126 активен высоким; выводы ПЛИС во время загрузки
      могут быть подтянуты вверх. Внешние pull-down 4,7–10 кОм на OE, чтобы буферы молчали до образа.
- [ ] **Питание выходной стороны от VREF** цели, а не от 3,3 В зонда. 74LVC гарантирован от 1,65 В;
      для 1,2 В — 74AUP1G126 или AXC. Ioff у LVC/AUP/AXC: при VREF = 0 выходы в Z, цель не питается
      через буфер.
- [ ] **nRESET открытым стоком на 126:** вход буфера на земле, OE — данные.
- [ ] **SWDIO:** направлением управляет ПЛИС, переключение в тот же такт, что разворот SWD.

Гейтвар: те же `dbg_shift`, `dbg_swd`, `swo_rx`, `dbg_phy` в образе GW5AT. Канал команд — своя пара
конечных точек USB 3.0 рядом с EP1 IN трассы. Выбор, кто разбирает CMSIS-DAP:

| Вариант | Плюсы | Минусы |
|---|---|---|
| а) Демон на ПК: свой протокол по USB → OpenOCD/pyOCD | ничего лишнего в ПЛИС | отдельная программа, не «подключил и работает» |
| б) Софт-ядро RISC-V (PicoRV32/VexRiscv) с free-dap в ПЛИС | нативный CMSIS-DAP v2, тот же код, что на CH569 | ресурсы GW5AT-15, отладка ещё одного процессора |
| в) CMSIS-DAP целиком в гейтваре (как в ORBTrace) | быстро, без процессора | большой объём работы, свой код вместо free-dap |

Решение — после замера свободных ресурсов в образе `usb3d`. Предварительно: (б), если влезает; иначе (а).

**Готово, когда:** на SLogic16U3 с адаптером проходят критерии D3 и D4, трасса и отладка работают одновременно.

### D7. Двухпроводные режимы: Spy-Bi-Wire и cJTAG

**Цель:** закрыть cJTAG из набора MIPI20; SBW — попутный бонус.

- **Spy-Bi-Wire (MSP430)** — полигон: на одной линии в трёх слотах на такт передаются TMS, TDI и TDO,
  как в OScan1. Протокол открыто описан (SLAU320). Переходник: SWCLK → TEST (SBWTCK), SWDIO → RST (SBWTDIO).
  Драйвер для mspdebug. Плат MSP430 на стенде с избытком.
- **cJTAG OScan1** — прозрачный мост `oscan1`: хост говорит обычным 4-проводным JTAG (CMSIS-DAP
  ничего не знает о cJTAG), ПЛИС переводит такты в OScan1 и сама выдаёт последовательность активации TAP.7.
  Поддерживаем классы T3/T4 (OScan1); звёздные топологии и остальные форматы 1149.7 — вне рамок.
- **Модель TAP.7** (`test/models/tap7.h`) для Verilator; заодно — TAP.7 в гейтваре Tang Nano 9K как
  управляемая мишень.
- **Целевая плата:** TI LaunchPad на CC13xx/CC26xx (например, CC2652R или CC1310) — у них двухпроводной
  cJTAG по умолчанию. На стенде такой нет — **купить**. TM4C123 и C2000 cJTAG не используют.

**Готово, когда:** SBW: mspdebug читает ID и шьёт MSP430. cJTAG: OpenOCD через наш мост читает IDCODE
ICEPick на CC26xx и шьёт его.

## 4. Тестовые цели

| Плата | Что на ней проверяем | Этапы |
|---|---|---|
| STM32F4-Discovery (STM32F407) | JTAG, SWD, SWO, ETM; основная цель | D0–D6 |
| Nucleo-144 (если есть) | то же на другом ядре (M7/H7), PE2–PE6 на Zio | D3–D6 |
| Nucleo-64 | только SWD и SWO (порта E и параллельной трассы нет) | D3–D4 |
| TI EK-TM4C123GXL | JTAG, SWD, SWO, переход JTAG↔SWD на чужом кремнии; ETM нет | D2–D4 |
| TI C2000 LaunchPad | цепочка JTAG с ICEPick: IDCODE, обход роутера; отладка ядра C28x закрыта | D2 |
| MSP430 LaunchPad | Spy-Bi-Wire, 4-проводной JTAG старых MSP430 | D7 |

## 5. Правила работы на железе

Для работы в Code-режиме с доступом к стенду (в том числе без присмотра):

- **Option bytes STM32 не трогаем никогда.** Ошибка в RDP уровня 2 закрывает чип необратимо.
  Стирание и запись флеша — можно.
- ПЛИС Tang Nano грузится в SRAM (`openFPGALoader -b tangnano20k`), во флеш — только по просьбе.
- Перемычки CN3, питание плат и переключение проводов — руками человека; агент только просит.
- TgtPwr и любые 5 В на цель — не включать.
- Перед каждым опытом на железе — тест в Verilator того же гейтвара (`make -C gw test`).
- Всё, что сделано и намерено, — в `doc/debug-journal.md`: команды, частоты, результаты, неудачи.

Что должно стоять на машине стенда: openFPGALoader, OpenOCD (с remote_bitbang и cmsis-dap), socat,
Python 3 с pyserial, Verilator 5, Yosys с `synth_gowin`, nextpnr-himbaechel или Gowin EDA, sigrok/PulseView,
mspdebug (для D7).

## 6. Риски и открытые вопросы

1. Скорость UART BL616 — от неё зависят этапы D1–D4 на стенде. Если она низкая, D2–D4 можно сразу
   перевести на HSPI через CH569 (шаг 0).
2. Максимальный TCK на проводах стенда: ожидание 5–10 МГц без подстройки выборки, 20–30 МГц с ней.
3. Перекрёстные помехи трассы и отладки при одновременной работе на проводах — проверить на D3.
4. SLogic16U3: свободные ресурсы GW5AT-15 после `usb3d` — решают вариант разбора CMSIS-DAP на D6.
5. Скорость SWO по Manchester у STM32F407 и точность восстановления такта — замерить на D4.
6. cJTAG: поведение ICEPick CC26xx после активации и совместимость с OpenOCD — главный неизвестный на D7.
7. VID:PID: образ SLogic сейчас работает на тестовом `1209:0001`; свой PID (`1209:3450`, загрузчик `3451`)
   запрашивается на pid.codes, когда в репозитории будет схема адаптера или платы зонда B.

# BE-U1000: журнал приёма трассы N-Trace

Продолжение [трассы STM32](slogic-trace-journal.md): тот же приёмник на SLogic16U3, но источник —
RISC-V микроконтроллер BE-U1000 («Байкал Электроникс») на отладочной плате EVU-BA-2.5, протокол —
RISC-V N-Trace через PIB (Pin Interface Block). Блоки **«Для статьи»** — повороты и находки, из
которых потом складывается рассказ.

Источники:

- [`doc/baikal/EVU-BA-2.5_Tech.pdf`](baikal/EVU-BA-2.5_Tech.pdf) — описание платы (BE-U-TD-RU#1734, v2.5.4), на
  стр. 24–28 — **принципиальная схема** (листы 1–5 из 7; без неё вывод про QSPI-флеш ниже не

## Итог

### Шаг 2: ядро 200 МГц, BTM и HTM, фильтры (2026-10-25)

Ядро 0 — PLL 200 МГц (шина и периферия 100 МГц), трасса — `tclk` 50 МГц. Прошивка та же, но в цикле
добавлена `bits(i)`: внутренний цикл на `nbits` шагов с ветвлением по битам `i` (2 условных перехода
на шаг); `nbits` и `pat` (фиксированный узор вместо `i`) меняются по SBA на ходу. Все записи ниже
разобраны до инструкций **без единой ошибки пути**; где были потери (Error), декодер перезапускался
по следующей синхронизации.

**BTM против HTM.** Трафик — байт трассы на восстановленную инструкцию; полоса PIB на 50 МГц —
400 Мбит/с, ядро на 200 МГц выполняет ~200 млн инструкций/с, т. е. без потерь проходит не больше
~2 бит на инструкцию.

| `nbits` (условных на проход) | BTM, бит/инстр | HTM, бит/инстр | HTM легче в | Потери BTM (Error за 0,65 мс) | Потери HTM |
|---|---|---|---|---|---|
| 0 (2) | 4,65 | 4,24 | 1,1 раза | 243 | 163 |
| 8 (18) | 3,21 | 1,97 | 1,6 раза | 142 | 0 |
| 32 (66) | 2,92 | 1,12 | 2,6 раза | 201 | 0 |
| 128 (258) | 2,86 | **0,68** | **4,2 раза** | 172 | 0 |

Выигрыш HTM целиком зависит от кода: HTM сжимает только условные переходы (бит в HIST вместо
сообщения DirectBranch на каждый взятый), а косвенные — возвраты, вызовы через указатель — стоят
столько же. В цикле с 4 косвенными переходами на проход разница 1,6 раза; «раза в 3» и больше — на
коде, где условных переходов на порядок больше, чем вызовов и возвратов. **BTM на ядре 200 МГц не
пролезает в 50 МГц PIB ни на каком коде, HTM — на всём, кроме кода из одних вызовов.**

**Stall** (`TR_TE_INST_STALL_EN`, `nbits` = 8): BTM без stall — 1,68 млн проходов/с и 172 Error за
запись; со stall — 1,31 млн (**−22 %**) и ни одной потери; HTM со stall и без — 1,67 млн, потерь нет
(ядро не ждёт). `TR_TE_INST_STALL_OR_OVERFLOW` (бит 12) при этом выставлен.

### Что из N-Trace реализовано в BE-U1000

Проверено открытием (записать единицы, прочитать) и опытами; RM v1.3.0 местами ошибается.

| Возможность (Trace Control Interface / N-Trace 1.0) | BE-U1000 | Как проверено |
|---|---|---|
| Режимы `trTeInstMode` | **3 — BTM, 6 — HTM** (0..2 → 0, 3..5 → 3, 6..7 → 6). RM: «2 — HTM» — неверно | запись всех значений |
| Формат | только N-Trace (`trTeFormat` = 1) | запись 7 → 1 |
| Периодическая синхронизация `trTeInstSyncMode/Max` | поля записываются (режимы 1–3) | по сообщениям, 2⁸ — в работе |
| Stall (`trTeInstStallEna`) | **есть**, работает | −22 % скорости, 0 потерь |
| Переполнение | Error (ETYPE 0, ECODE 4) + синхронизация с **SYNC = 5**, а по спецификации должно быть 7 | ядро 200 МГц, BTM |
| Триггеры → trace on/off (`trTeInstTrigEnable`) | **есть** (бит 11 записывается, в RM — нет) | см. «Фильтры» |
| Поле SRC (`trTeSrcBits/ID`, `trTeInhibitSrc`) | нет: SRC_BITS = 0; InhibitSrc записывается, но ни на что не влияет | открытие |
| Ownership / контекст (`trTeContext`) | нет (только чтение, 0) | открытие |
| `trTeInstFeatures`: NoAddrDiff, implicit return, branch prediction, jump target cache, repeated history, all jumps, extend MSB | **ничего** (регистр — нули, запись не держится) | открытие |
| RepeatBranch, HREPEAT | не встречаются (repeated history нет) | — |
| Фильтры `trTeInstFilters`, `trTeFilter*`/`trTeComp*` (0x400–0x7FF) | **нет** | открытие |
| Трасса данных `trTeData*` | **нет** | открытие |
| Внешние триггеры `trTeTrig*` (0x50–0x58) | нет | открытие |
| Метки времени `trTs*` | есть: 32 бита, пределитель 1/4/16/64, считает только тип 2 (системная шина, `hclk`); тип 3 (такт ядра) и 4 стоят. **В каждом сообщении — абсолютное значение**, по спецификации вне синхронизаций должна быть разница | запись `trTsEnable`, ×1,8 трафика |
| HIST | 32 бита (31 исход + стоп-бит) | порог: `nbits` 14 → 15 |
| ResourceFull по HIST | **без TCODE** и с молчаливым сбросом I-CNT — см. запись «ResourceFull без заголовка» | `pat`, перебор |
| ResourceFull по I-CNT (RCODE 0) | не вызывали (нужен линейный код длиннее предела I-CNT) | — |
| Сообщения, встреченные на линиях | DirectBranch 3, IndirectBranch 4, Error 8, ProgTraceSync 9, IndirectBranchSync 12, IndirectBranchHist 28, ProgTraceCorrelation 33 (EVCODE 4 при trace-off), ResourceFull (без TCODE) | записи `runs/beu1000/` |
| SYNC | 2 — периодическая **и** trace-notify (должно быть 6), 5 — включение трассы **и** после переполнения (должно быть 7) | опыты |
| PIB | только 4 бита, без делителя; регистры повторяются каждые 8 байт по всему окну 4 КБ | открытие |
| RAM-приёмник | только SRAM (`HAS_SRAM`), `Limit` фиксирован (0x3FC), `WP`/`RP` записываются | открытие, в работе не проверяли |
| Выбор ядра | `SYSCR0.TRACESEL` (CRU) или `TRACE_SEL` 0x4000_A014 — последний виден только ядру 2 (у ядра 0 там ROM) | чтение |

### Фильтры

Собственных фильтров у кодера нет — ни адресных диапазонов (`trTeFilter*`), ни компараторов
(`trTeComp*`), ни фильтра по режиму привилегий. Остаётся то, что даёт отладочный модуль RISC-V:

- **Триггеры ядра с действием trace-on / trace-off / trace-notify** (Debug Spec, `mcontrol.action`
  2/3/4). У ядра 0 **четыре** триггера, все `mcontrol` (`tinfo` = 4), и они минимальные: только
  точное совпадение адреса (`match` = 0; «≥», «<», маски и NAPOT не держатся), **без цепочек**
  (`chain`), без сравнения данных (`select`) и без `timing`; зато выполнение, чтение и запись и выбор
  режима M/S/U. Итого фильтр — четыре точки «адрес → включить / выключить / пометить», диапазон
  адресов одним условием не задать.
- Включаются битом `trTeInstTrigEnable` (11), `trTeInstTracing` при этом не ставится — его дёргают
  триггеры. Опыт: trace-on на входе в `op_a`, trace-off на входе в `op_c` — трасса включается **на**
  первой инструкции `op_a` (ProgTraceSync, SYNC = 5, I-CNT = 0, F-ADDR = `op_a`) и выключается
  **после** первой инструкции `op_c` (ProgTraceCorrelation, EVCODE = 4, I-CNT = 2, пустой HIST): за
  запись `op_c` попала в трассу ровно одной инструкцией `lui` 340 раз из 340 входов, остальные её
  инструкции — ни разу. Трафик — 2,42 бит/инстр против 1,97 без фильтра (каждое включение — полная
  синхронизация, 7 байт).
- trace-notify на `op_b` — синхронизация с полным адресом сразу после первой инструкции `op_b` на
  каждый вход (340), трасса не прерывается; код причины — SYNC = 2, а не 6.
- Программно: регистры трассера видны ядру (0x1510_4000 в его карте памяти), так что программа может
  сама ставить и снимать `trTeInstTracing` вокруг нужного участка. Не проверяли.

### Шаг 1: трасса инструкций N-Trace на 25 и 50 МГц (2026-10-25)

Источник — своя прошивка [`fw/main.c`](../tools/slogic/trace/beu1000/fw/main.c) в TCMA ядра 0 (ядро на
`sys_clk` 25 МГц от CLKI): цикл с условным переходом по чётности счётчика и вызовом через указатель
`ops[i % 3]`. Трассер — branch trace (BTM), периодическая синхронизация каждые 2⁸ сообщений,
настраивается по SBA с ПК, ядро не останавливается. Приёмник — тот же образ `tracela.v`, режим 2
(IDDR от TRACECLK), IODELAY 224, разбор — [`ntrace.py`](../tools/slogic/trace/beu1000/ntrace.py): MSEO →
сообщения → поля → путь программы по ELF.

| `tclk` (= TRC_CLK) | Запись (65 536 полубайт) | Сообщений | Инструкций | Ошибок пути | Порядок `op_a→op_b→op_c` |
|---|---|---|---|---|---|
| 25 МГц, `sys_clk` | ~1,3 мс, простоя 67 % | 3185 | 21 629 | 0 | 848 вызовов, 0 нарушений |
| 25 МГц, PLL 200 / 8 | ~1,3 мс | 3186 | 21 364 | 0 | 838 / 0 |
| 50 МГц, PLL 200 / 4 | ~0,65 мс, простоя 83 % | 1591 | 11 495 | 0 | 451 / 0 |

Все периодические синхронизации (`ProgTraceSync`, SYNC = 2) пришли ровно туда, куда декодер дошёл
сам по I-CNT. **На 50 МГц трасса чистая** — дальше упирается в жгут, как и у STM32. Записи —
`tools/slogic/trace/runs/beu1000/`, разбор первой — `runs/beu1000/show.txt`.

### Что выяснили на железе

- **TRC_CLK = `tclk`**, данные по обоим фронтам: один байт трассы на такт `tclk`. Делителя в PIB нет
  (`TR_PIB_DIVIDER` = 0, только чтение), режим — только 4 бита. Скорость задаёт `tclk` из CRU:
  `CLKSEL.TCLK_SEL` (0 — `sys_clk`, 1 — делитель от PLL) и `CLKCR1.TCLKDIV`; максимум по RM — 100 МГц.
- **TRC_CLK идёт, только когда трассеру есть что слать** (включён кодер или калибровка). При
  включённом PIB и выключенном кодере линии и такт стоят — при первом заходе это выглядело как «от PLL
  такта нет».
- **Данные меняются по фронту TRC_CLK, а не в середине бита**, хотя `TR_PIB_CLK_CENTER` читается как 1.
  Смена приходит на 0,6–2,2 нс позже фронта (на входе ПЛИС; D0 и D2 позже D1 и D3), одинаково на 25 и
  50 МГц. Приёмник выбирает данные **после** смены: IODELAY 176–255 (2,2–3,2 нс) годится для всех
  линий; до следующей смены — полбита (10 нс на 50 МГц).
- **Калибровка есть, но бит не там, где в RM.** Запись бита 9 (`TR_PIB_CALIBRATE` по RM) читается
  как бит 8, а узор `A 5 A 5 0 F F 0` из спецификации идёт на линии — при работающем трассере.
- `TR_TE_INST_MODE`: 3 — branch trace, 6 — branch history, как в спецификации (RM пишет 2 — это не
  держится; поправлено на шаге 2).
  `trTeImpl` = 0x101 (версия 1.0, тип 1), `trRamImpl` = 0x1901 (только SRAM), `trTsControl` = 0x2000_0000
  (счётчик меток времени 32 бита).
- BE-U1000 **сбрасывается при каждом запуске OpenOCD** с конфигом платы (FTDI DD7 дёргает nSRST при
  входе в MPSSE): настройки трассера, сделанные одним запуском, к следующему пропадают. Отсюда —
  постоянный сервер OpenOCD (`ocd.py`).

### Шаг 0: что читали и куда подключать (2026-10-25)

Подключение (подробно — в «Стенд»): **PB0–PB3 → CH8–CH11, PB4 → CH12, земля — XP10 контакты 4 и 20**,
всё на разъёме XP10 платы. **Перед подключением — снять R5 (22 Ом)** у QSPI-флеш DD1, иначе трасса
пойдёт и во флеш (см. запись «Где взять PIB на плате»).

План первого опыта: режим калибровки PIB (`trPibCalibrate`) — он не требует ни кодера, ни
работающей программы, только два регистра PIB; на линиях должен крутиться узор `A 5 A 5 0 F F 0`.

## Что выяснили о трассе BE-U1000 (по документам, до железа)

*Написано до Reference Manual и до железа; поправки — в «Что выяснили на железе» выше.*

### Блок трассировки

- Ядра 0 и 1 (CloudBEAR BR-350, RV32IMCBFNAU[P], до 200 МГц) отдают трассу через интерфейс RVT в
  общий **Tracer**. Трассер **в каждый момент работает только с одним из ядер 0 или 1**. Ядро 2
  (BM-310, «PIO-ядро») трассы не имеет, зато в его собственном окне 0x4000_A000 лежит блок
  «PIO, Software JTAG и **Trace Select**» — видимо, это и есть переключатель ядра для трассера.
- Компоненты трассера в карте памяти ядер 0/1 (область высокоскоростной периферии):

| Адрес | Компонент (даташит) | Компонент по Trace Control Interface | Обязательные регистры |
|---|---|---|---|
| 0x1510_4000 | Tracer encoder control interface | Trace Encoder | `trTeControl` +0x000, `trTeImpl` +0x004 |
| 0x1510_5000 | Tracer RAM control interface | Trace RAM Sink | `trRamControl`, `trRamImpl`, `trRamStart/Limit/WP` |
| 0x1510_6000 | Tracer PIB control interface | Trace PIB Sink | `trPibControl` +0x000, `trPibImpl` +0x004 |
| 0x1510_7000 | Tracer SRAM interface | (окно в буфер RAM-приёмника) | — |

  Воронки (Funnel) и моста ATB нет: один кодер — один приёмник за раз. Сверка на железе — по
  `tr??Impl[11:8]` (тип компонента): кодер `0x1`, PIB `0xA`; `trTeImpl[3:0]` = 0 означает
  доратификационную версию 0 (SiFive, 2020) — тогда раскладка битов другая.
- Доступ внешнего отладчика к этим регистрам по спецификации — через **SBA** (System Bus Access)
  отладочного модуля RISC-V, т. е. чтение/запись памяти, пока ядро бежит. Альтернатива — программа
  на самом ядре пишет регистры сама (так было с ITM/ETM на STM32).

### PIB по спецификации

`trPibControl` (0x1510_6000):

| Биты | Поле | Что ставим |
|---|---|---|
| 0 | `trPibActive` | 1 — вывести из сброса (ждать, пока прочитается 1) |
| 1 | `trPibEnable` | 1 — последним, после настройки и запуска приёмника |
| 3 | `trPibEmpty` (RO) | 1 — буферы пусты |
| 7:4 | `trPibMode` | **10 = TRC_CLK + 4 TRC_DATA** (WARL: записать и прочитать — принято ли) |
| 8 | `trPibClkCenter` | **1 — фронт TRC_CLK в середине бита** (WARL, может не быть) |
| 9 | `trPibCalibrate` | 1 — узор калибровки вместо трассы |
| 14:12 | `trPibAsyncFreq` | частота вставки байтов простоя для выравнивания |
| 31:16 | `trPibDivider` | делитель входного такта: f = f_in / (N + 1); ширина и источник такта — по реализации |

Порядок: Active → (Mode, Divider, ClkCenter, Calibrate) → запустить приёмник → Enable.

- **Данные идут по обоим фронтам TRC_CLK (DDR), как у TPIU STM32.** При `trPibClkCenter` = 0
  фронты TRC_CLK совпадают со сменой данных, бит = период делённого такта, TRC_CLK = f / 2. При
  `trPibClkCenter` = 1 TRC_CLK вдвое медленнее (f / 4) и его фронты — в середине бита.
- **Для нашего приёмника нужен `trPibClkCenter` = 1.** Режим 2 приёмника (IDDR от TRACECLK)
  защёлкивает данные фронтом такта, а IODELAY двигает выборку максимум на 255 × 12,5 пс ≈ 3,2 нс.
  При ClkCenter = 0 и TRC_CLK 25 МГц полбита — 10 нс: задержкой не дотянуться, нужен сдвиг такта
  на 90° через PLL ПЛИС (спецификация так и предлагает пробникам). Если бит WARL не примется —
  делать PLL.
- Порядок бит: байт идёт младшим полубайтом вперёд, TRC_DATA[0] — младший бит. Как у TPIU.
- Калибровка в 4-битном режиме: байты `5A 5A F0 0F` → на линиях `A, 5, A, 5, 0, F, F, 0` по
  кругу. Готовый тест проводки и перестановки линий (то, что на STM32 пришлось делать перебором
  24 перестановок по `FF 7F`).

### Протокол N-Trace на линиях

- Сообщение — последовательность байт; в каждом байте **MSEO[1:0] — два младших бита, MDO[5:0] —
  шесть старших**. MSEO = 00 — первый байт сообщения и байты полей фиксированной длины; 01 —
  последний байт поля переменной длины; 11 — последний байт сообщения; 10 — резерв.
- Простой — байт `0xFF` (MSEO = 11, MDO = 111111). Кадров форматтера, ID источников и
  синхронизации `FF FF FF 7F` нет вообще: выравнивание — по простоям.
- **Простой может быть любым числом фронтов, в том числе нечётным** (раздел «PIB Idle Cycles
  Explained»): в 4-битном режиме следующее сообщение может начаться на любом полубайте. Значит,
  разбор не может резать поток на байты один раз — после каждого простоя выравнивание заново:
  первый полубайт с младшими битами ≠ `11` после серии `F` — начало сообщения (MSEO = 00).
  Для 1/2/4-битных режимов PIB обязан периодически вставлять хотя бы один байт простоя и всегда —
  перед синхронизирующим сообщением.
- Первый байт: MSEO = 00, MDO = TCODE (6 бит). Эталонный декодер `NexRv` умеет разбирать поток
  байт и восстанавливать путь программы по ELF — его и берём за образец.

|---|---|---|---|---|
| 1 | PB0 (12) | PIB_D[0] | CH8 | N11 |

| 3 | PB2 (9) | PIB_D[2] | CH10 | N10 |

Распределение каналов — как у STM32 (`LANES = "0123"`, такт на CH12), приёмник менять не надо.
PB3 стоит на другом конце разъёма (контакт 19), поэтому и вторая земля — с контакта 20, рядом с ним.

Плата: загрузка — сценарий «JTAG EXT» (перемычки XP1 DBG-M2-M1-M0 = 0100), отладчик — FTDI DD7 на
плате через XS2 (JTAG на PA0–PA4). Тактирование — от генератора 25 МГц (перемычка CLK на XP1
снята): для трассы нужен стабильный такт, внутренний RC-генератор 12–32 МГц плавает.

## 2026-10-25. Где взять PIB на плате

У BE-U1000 три варианта выводов PIB (табл. 3-2 и 5-4/5-5 даташита):

| Вариант | Выводы | АФ | Что ещё на этих выводах на EVU-BA-2.5 |
|---|---|---|---|
| PB0–PB4 | D0–D3, CLK | АФ4 | QSPI1 → флеш DD1 (MT25QL128), XP10 |
| PC11–PC15 | D0–D3, CLK | АФ3 | PC13 — кнопка SB1 с RC-цепочкой; PC15 — EN ключа питания USB (DD4); XP8 |
| PC0–PC4 | D0–D3, CLK | АФ5 | PC0 — светодиод LD1; PC4 — перемычка MODE[2] (при «JTAG EXT» стоит, подтяжка к 3,3 В); PC0–PC3 — ещё и вариант JTAG |

Вариант PC0–PC4 отпадает сразу: PIB_CLK на выводе конфигурации загрузки с внешней подтяжкой.

**Для статьи: трасса, которая стирает флеш.** На блок-схеме платы у порта B нарисована QSPI-флеш,
и по схеме видно, что она висит прямо на будущих линиях трассы: PB0 — её S# (выбор кристалла),
PB1 — такт C, PB2 — DQ0, PB3 — DQ1 (выход флеш!), PB4 — W#/DQ2, PB5 — HOLD#/DQ3. Последовательные
0 Ом R53, R47–R51 у выводов МК не спасают — разъём XP10 по схеме подключён после них, на стороне
флеш. Если пустить трассу как есть, флеш видит на S#, C и DQ0 случайный поток: рано или поздно
она получит «чтение» и начнёт выдавать данные на DQ1 навстречу PIB_D[3] (два выхода друг против
друга через 22 Ом — ошибки в трассе и ток через выводы), а в quad-режиме — и на DQ0–DQ3. Хуже
того, случайная пара команд «разрешить запись» + «стереть» — и флеш потеряет содержимое. Перевести
её программно в глубокий сон тоже не выход: выход из сна — однобайтовая команда `0xAB`, которая в
случайном потоке рано или поздно встретится.

Лечится одним резистором: **S# флеш подтянут к 3,3 В резистором R4 10 кОм на стороне флеш, а к PB0
идёт через R5 22 Ом.** Снять R5 — флеш навсегда не выбрана, её выходы в третьем состоянии, остальные
линии видят только входы флеш (единицы пФ) и отводы 22 Ом. Цена — недоступна загрузка «QSPI»;
вернуть — запаять R5 обратно (или 0 Ом).

Вариант PC11–PC15 требует двух переделок вместо одной: у кнопки SB1 на PC13 стоит гасящая цепочка
100 Ом + 100 нФ на землю (на 25 МГц это просто 100 Ом на землю — PIB_D[2] будет убит), её отрезать
снятием R22 (0 Ом); PC15 через R43 (0 Ом) управляет ключом питания USB OTG — PIB_CLK стал бы дёргать
VBUS на XS1. Плюс выводы PC11–PC14 — ещё и запасной JTAG. Поэтому — **PB0–PB4 и снятый R5.**

## Инструменты и команды

Файлы — в [`tools/slogic/trace/beu1000/`](../tools/slogic/trace/beu1000/).

| Файл | Что делает |
|---|---|
| `openocd.cfg` | OpenOCD SDK к BE-U1000 через FTDI платы: без остановки ядра, свои порты (6668/4446/3337), `riscv virt2phys_mode off` и `set_mem_access sysbus` для CORE_0 — память читается на бегущем ядре |
| `trace.tcl` | процедуры: `pll nr nf od`, `core cdiv pdiv` (ядра и шина от PLL), `tclk src [div]`, `pins [ds]` (АФ4 на PB0–PB4, крутизна), `pib_on`, `te_on [mode sync syncmax stall trig]`, `te_off`, `trig_set idx addr act`, `trig_clear`, `discover base` (открытие по спецификации), `tr_status` |
| `ocd.py` | постоянный OpenOCD в фоне и команды ему через Tcl-порт (каждый новый запуск сбрасывает МК) |
| `fw/` | источник: `main.c` (известная последовательность ветвлений; `pat` 0x4002_0000, `nbits` 0x4002_0004, `n` 0x4002_000C), `start.S`, `link.ld` (код в TCMA, данные в TCMB) |
| `ntrace.py` | `cal` — окно каждой линии по IODELAY на узоре калибровки; `cap`/`decode` — MSEO → сообщения → поля (табл. N-Trace 1.0) → путь программы по ELF (BTM и HTM, ResourceFull без TCODE, RepeatBranch, Error, остановка трассы) с проверкой синхронизаций и порядка вызовов; `table` — исходник → инструкция → сообщение → декодер. `cap --save` кладёт копию ELF рядом с записью |

```sh
cd tools/slogic/trace
export RLN_BEU_USB=1-1 RLN_FPGA_USB=1-2    # две одинаковые FT2232H: плата и наша (места на шине USB)
make -C beu1000/fw
openFPGALoader -c ft2232 --busdev-num 1:$(cat /sys/bus/usb/devices/1-2/devnum) -m gw/tracela.fs

python3 beu1000/ocd.py "halt; load_image $PWD/beu1000/fw/trace.elf; reg pc 0x40010000; resume"
python3 beu1000/ocd.py "pins 3; pll 1 48 6; tclk 1 4; pib_on; te_on 3 1 4; tr_status"   # 50 МГц
python3 beu1000/ocd.py "core 1 2; te_off; te_on 6 1 4 0"   # ядро 200 МГц, HTM (stall — 4-й аргумент)
python3 beu1000/ocd.py "wr 0x40020004 32"                  # nbits
python3 beu1000/ocd.py "te_off; te_on 6 1 4 0 1; trig_set 0 0x4001004c 2; trig_set 1 0x40010076 3"  # фильтр
python3 beu1000/ocd.py 'discover $TR_TE'                   # открытие компонента
python3 beu1000/ocd.py 'wr $TR_PIB 0x203'          # калибровка (бит 9, читается как 8)
python3 beu1000/ntrace.py cal                      # окно линий
python3 beu1000/ocd.py 'wr $TR_PIB 3'              # обратно в трассу
python3 trace.py freq                              # TRC_CLK — строка «в домене TRACECLK»; читать дважды
python3 beu1000/ntrace.py cap --dly 224 --save runs/beu1000/x.json
python3 beu1000/ntrace.py table runs/beu1000/table-m6.json --start 0x4001011c --skip 3 --count 120
python3 beu1000/ocd.py --stop
```

Грабли:

- частотомер ПЛИС обновляется раз в 0,56 с: сразу после перенастройки показывает старый такт;
- `trace.py` и `openFPGALoader` без указания адаптера берут первую FT2232H — может оказаться плата;
- `pkill -f` по имени конфига убивает и собственный шелл (в его командной строке та же строка);
- `set_mem_access` из `taps.cfg` SDK применяется к последней созданной цели (CORE_2), не к CORE_0;
- адреса переменных прошивки сдвигаются при правках `main.c` — смотреть `nm fw/trace.elf`;
- компилятор вставляет свои условные переходы (`beqz len`, проверка `pat`) — их исходы тоже в HIST;
- стандартный `EVU_BA_2_5.cfg` SDK после сброса выводит PIB_CLK ещё и на PC4 (`IOAFCR4` = 0x88858888) —
  это вывод загрузочной перемычки MODE[2].

## 2026-10-25. Подключение: OpenOCD, сбросы, первый такт

В WSL не было ни одного USB-устройства — обе FT2232H (плата и наша для ПЛИС) были расшарены в
usbipd, но не подключены. Серийников у них нет, отличаются только местом на шине; плата — 1-1, наша —
1-2 (проверено: на 1-2 отвечает TAP Gowin `0x0001681b`). В цепочке JTAG платы три TAP с ID `0x1bafa001`
(ядра 2, 1, 0). `SBCS` отладочного модуля = 0x20040407: SBA есть, адрес 32 бита, доступ 8/16/32.

Первые же записи в регистры «не держались»: PIB, только что включённый, в следующем запуске снова
читался в сбросе. Списал было на смену такта, но метка в `IODSCR1` показала: **сбрасывается весь
кристалл при каждом запуске OpenOCD**. Дальше — один сервер на всю работу.

Ядро 0 после «JTAG EXT» стоит в загрузочном ROM на `0x4000124C` (шаг отладчиком не сдвигает PC — `wfi`
или переход на себя). Такт ядра проверен по `mcycle`: 55,1 млн тактов за ~2,1 с — 25 МГц, т. е.
`sys_clk` от CLKI (`SYSSR0.STRAP` = 0b00100: «JTAG EXT», CLK_STRAP = 0).

**Для статьи: калибровка, которой «нет».** По RM бит `TR_PIB_CALIBRATE` — девятый. Пишу `0x203`
(Calibrate + Enable + Active) — читается `0x1A3`: девятого бита нет, зато появился восьмой
(`TR_PIB_CLK_CENTER`, «только чтение, всегда 1»). Линии данных стоят. Вывод напрашивался — калибровки
нет. Но стоило включить кодер, и на линиях пошёл узор — сначала `a5f55ff0`, а при IODELAY 255 —
ровно `A 5 A 5 0 F F 0` из спецификации. Калибровка есть, просто идёт только при работающем
трассере, а бит в регистре читается со сдвигом.

## 2026-10-25. Окно линий и первая трасса

Перебор IODELAY на узоре калибровки (`ntrace.py cal`, 25 МГц): при крутизне выводов 0 (4,5 мА) D1 и D3
верны при 0–32 и 144–255, D0 — только 240–255, D2 — 208–255: смена данных приходит почти на фронт
TRC_CLK, и D0/D2 запаздывают. Крутизна 3 (18 мА) сдвинула смены на ~0,8 нс раньше: все четыре линии
верны при 176–255. На 50 МГц — те же 176–255 (смена на фиксированной задержке от фронта, а не в
середине бита). Рабочая точка — IODELAY 224.

После снятия калибровки — один простой: ядро в ROM крутится на месте, а у `wfi`/`j .` сообщений в
branch trace нет. С прошивкой `fw/` пошли сообщения: DirectBranch (TCODE 3), IndirectBranch (4) и
ProgTraceSync (9).

**Для статьи: байт за байтом.** Сообщение `10 e1 2b` (возврат из `inc_even`):

| Байт | MSEO | MDO | Что в нём |
|---|---|---|---|
| `0x10` | 00 — начало | 000100 | TCODE = 4, IndirectBranch |
| `0xE1` | 01 — конец поля | 111000 | B-TYPE = 00 (обычный косвенный переход), I-CNT = 1110 = 14 полуслов |
| `0x2B` | 11 — конец сообщения | 001010 | U-ADDR = 0xA → XOR 0x14 с прошлым адресом: `0x400100C6 ^ 0x14 = 0x400100D2` |

Периодическая синхронизация `24 89 a0 00 20 00 83`: TCODE 9, SYNC = 2, I-CNT = 2, F-ADDR = 0x40010050
(середина `op_a`) — полный адрес, от которого декодер стартует и с которым сверяется на ходу.

**Для статьи: трасса снова сама себя проверяет.** Три свидетельства, что разбор верен: каждая
периодическая синхронизация совпадает с адресом, куда декодер дошёл сам; последняя инструкция каждого
блока — именно тот переход, о котором сообщение (условный для DirectBranch, `ret`/`jalr` для
IndirectBranch); и вызовы `op_a → op_b → op_c` идут по кругу без пропусков — 848 подряд.

## 2026-10-25. Ядро 200 МГц: BTM, stall, HTM

`core 1 2` — ядра от PLL 200 МГц, шина и периферия 100 МГц (как `QSPI_clk_init` в SDK, но без
перезапуска PLL). Цикл прошивки — 1,68 млн проходов/с. BTM без stall: 172 Error за запись, после каждой —
синхронизация, декодер восстанавливается; со stall — ни одной потери ценой 22 % скорости ядра.

**Для статьи: HTM, которого нет.** RM v1.3.0: «`TR_TE_INST_MODE` 0x2 — Branch History Messaging,
0x3 — Branch Trace». Пишу 2 — читается 0, трассы нет. Перебор всех восьми значений: 0–2 → 0, 3–5 → 3,
6–7 → 6. Поле — ровно по спецификации (6 — HTM), RM ошибся в цифре. С `te_on 6` пошли
IndirectBranchHist (TCODE 28).

## 2026-10-25. ResourceFull без заголовка

На `nbits` = 32 HTM перестал сходиться, а в потоке появились пары сообщений с TCODE 33
(ProgTraceCorrelation — «трасса остановлена»), которых тут быть не должно: в паре первое меняется от
прохода к проходу, второе — постоянно; поле одно, переменной длины, 30 бит. И I-CNT в следующем
IndirectBranchHist — 14, хотя должен покрывать весь цикл `bits()`.

**Для статьи: сыщик с известным ответом.** Подбирать раскладку по случайным `i` — гадание, поэтому
прошивке дали переменную `pat`: при `pat` ≠ 0xFFFFFFFF в `bits()` идёт фиксированный узор, и
последовательность исходов известна заранее до бита. Дальше — по шагам:

1. Порог: `nbits` 14 (29 исходов на проход) — всё в IndirectBranchHist; 15 (31 исход) — появляется
   сообщение с первым байтом `04` (TCODE 1); 16 — `84` (TCODE 33). Бит 5 первого байта меняется с
   данными — значит, он **не TCODE**.
2. `pat` = 0, 1, 0x2000, 0x4000, 0x8000 при `nbits` = 16 (ожидается: `beqz` 0, пары `01`…, конец `00`):
   поле читается как HIST по стандарту (старший бит — стоп, под ним первый исход, младший — последний),
   но начинается **с бита 4** первого байта: при `pat` = 0x4000 первый байт стал `c4` — это исход
   `bnez` шага 14, и в следующем IndirectBranchHist осталось ровно три исхода вместо четырёх.
3. Итог: младшие 4 бита — `0001`, дальше 32 бита HIST. Это поля ResourceFull по спецификации — RCODE = 1
   (4 бита) и RDATA = HIST, — **но без 6-битного TCODE 27 впереди**. Отсюда и «TCODE 1/33»: в
   заголовок попадают RCODE и первые два бита истории.
4. I-CNT: после такого сообщения следующий IndirectBranchHist несёт I-CNT = 14 — ровно от условного
   перехода, который заполнил HIST, до `ret` (1+1+2+2+1+1+1+1+2+1+1 полуслов). Кодер **сбрасывает I-CNT
   на заполнении HIST, не передавая его** (по спецификации I-CNT сбрасывается только после передачи).
   Декодировать всё равно можно: идти по коду, пока не уйдёт последний бит HIST, — блок кончается на
   переходе, который его взял.

После этого все записи с ResourceFull разбираются без ошибок: `nbits` 15, 16, 32, 128, все `pat`.
Отличить такое сообщение от настоящего ProgTraceCorrelation можно по числу полей (у того их два —
I-CNT и HIST — плюс EVCODE/CDF), при включённых метках времени — пока нет (не проверяли).

## 2026-10-25. Фильтры и метки времени

Открытие (`discover`) показало, что у кодера кроме `trTeControl`, `trTeImpl` и `trTsControl` нет ничего:
окно 0x400–0x7FF (фильтры, компараторы), триггеры 0x50–0x58, трасса данных, `trTeInstFeatures` —
нули и запись не держат. Фильтровать можно только триггерами ядра — подробности в «Фильтры» выше.

**Для статьи: фильтр из отладчика.** Две строки — `trig_set 0 op_a 2` (trace-on) и `trig_set 1 op_c 3`
(trace-off) — и трасса идёт только от входа в `op_a` до входа в `op_c`. Кодер при этом делает всё
по спецификации: на выключении — ProgTraceCorrelation с причиной «трасса выключена», I-CNT и
пустым HIST (декодер знает, где остановилось), на включении — синхронизация с полным адресом.

Метки времени: `trTsControl` — тип 2 (системная шина), ~25 МГц на `hclk` = `sys_clk`, 100 МГц после
`core 1 2`. С `trTsEnable` поле TSTAMP приходит в **каждом** сообщении, и всегда абсолютное (6840276,
6840288, …), — трафик HTM вырос с 1,97 до 3,55 бит/инстр, пошли потери (47 Error). По спецификации
абсолютная метка нужна только в синхронизациях, в остальных — разница с предыдущей.

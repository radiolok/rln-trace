# Как вскрывали libUHSIF.a: методика

Пошаговый разбор закрытой статической библиотеки WCH для RISC-V-микроконтроллера: от `.a` до описания
регистров периферии. Результаты лежат в [ch32h417-uhsif.md](ch32h417-uhsif.md), скрипты — в
[`tools/uhsif-re/`](../tools/uhsif-re/). Код библиотеки в репозиторий не копируем: здесь только
методика, адреса и выводы.

Исходные условия: библиотека `libUHSIF.a` из [openwch/ch32h417](https://github.com/openwch/ch32h417).
В публичном `ch32h417.h` от UHSIF есть только базовый адрес и номер прерывания: `UHSIF_TypeDef`
упомянут, но не определён. Руководство по UHSIF описывает шину со стороны ПЛИС, а не регистры. Инструменты: Ghidra 12.1.4, Python
(pyelftools, capstone, unicorn, ziglang ради `ld.lld`), binutils хоста (`ar`, `nm`, `readelf`).
RISC-V-тулчейн WCH (MounRiver) для разбора не понадобился.

## 1. Осмотр банки

```sh
ar x libUHSIF.a            # → lib.o
readelf -A lib.o           # Tag_RISCV_arch
readelf -SW lib.o          # секции
nm lib.o                   # символы
```

Что сразу видно:

- **Символы на месте.** Библиотека не урезана: имена функций, таблиц и переменных сохранились, и по
  ним уже понятна архитектура (микрокод `UhsifWavedata_*`, таблица регистров `UhsifRegValue`,
  дескрипторы `SOCKET_DSCR_*`).
- **`-ffunction-sections -fdata-sections`.** Каждая функция и каждая таблица лежат в своей секции,
  у всех адрес 0. В таком виде дизассемблер видит десятки обрывков без связей между ними.
- **Архитектура `rv32imac_zba_zbb_zbc_zbs_xw2p2`.** Битовые расширения и собственное расширение WCH
  `xw2p2`. Ни capstone 5, ни Ghidra на импорте его не знают: это главная ловушка, см. шаг 4.
- **Внешние зависимости** (`nm | grep ' U '`): `GPIO_Init`, `RCC_*`, `memcpy`, `memset`,
  пользовательские колбэки и millicode `__riscv_save_N` / `__riscv_restore_N` (сборка с
  `-msave-restore`, у функций нет обычного пролога).

Публичный заголовок `ch32h417_uhsif.h` и пример `ch32h417_uhsif.c` из того же каталога дают прототипы
и реальный порядок вызовов. Это готовый сценарий для эмуляции (шаг 6).

## 2. Перелинковка объекта в плоский образ

Вместо того чтобы разбираться с релокациями внутри дизассемблера, объект линкуется сам по себе в
обычный ELF с выдуманной картой памяти:

- код и константы — с `0x00010000`, данные — с `0x20000000` ([`link.ld`](../tools/uhsif-re/link.ld));
- каждый внешний символ — абсолютный адрес-ловушка `0x00F00000 + 16·i` через `--defsym`;
- `--no-relax`, чтобы линкер не переписывал последовательности `auipc+jalr`.

`ld.lld` берётся из pip-пакета `ziglang`: полноценный кросс-линкер без установки тулчейна. После
этого у каждой инструкции настоящий адрес, у каждого обращения к таблице — настоящий операнд, а
адреса-ловушки сразу видны в коде как вызовы внешних функций.

## 3. Первый проход Ghidra

`analyzeHeadless` с Java-скриптом, который декомпилирует все функции в один текстовый файл
([`DumpAll.java`](../tools/uhsif-re/DumpAll.java)). GUI не нужен, проход повторяется одной командой.

Результат: `UHSIF_Cfg`, `UHSIF_GPIO_Init`, `SOCK_CFG_INIT` читаются почти целиком, и из них уже
видны базовые адреса блока. `UHSIF_IRQHandler`, `UHSIF_Trans_Cfg`, `UHSIF_Line_Cfg` и
`UHSIF_Reg_Cfg` обрываются на `halt_unimplemented()`. Кроме того, из-за `__riscv_save_N` декомпилятор
теряет аргументы функций (`extraout_a2` вместо параметров).

## 4. Опознание «неизвестных» инструкций

Независимый линейный дизассемблер на capstone ([`disasm.py`](../tools/uhsif-re/disasm.py)) помечает всё,
что не декодировалось, и отдельно ищет инструкции с плавающей точкой: FPU в этой сборке нет, так
что любая `c.fld`/`c.fsd` — подозрительная.

Нашлись две группы.

**16 стандартных инструкций Zba/Zbb/Zbs**, которых нет в capstone 5: `sh2add`, `sh3add`, `zext.h`,
`bseti`, `bclri`. Опознаются вручную по полям funct7/funct3 из спецификации bitmanip. Ничего
секретного здесь нет: инструменты просто отстают от спецификации.

**14 инструкций в кодировках `c.fld` / `c.fsd`** (квадрант 0, funct3 = 001 и 101). Это и есть `xw2p2`.
Значение выводится из контекста, без документации:

1. В `UHSIF_Line_Cfg` адрес считается как `UHSIF_Para + line·8` (`sh3add`), то есть указывает на
   `UHSIF_Para.Stu[line]`. Структура известна из публичного заголовка: байты `Thread_Enable`,
   `Thread_Dir`, `Socket_Count`, затем слово `Water_Mark_Value`.
2. Сразу после этого идут три «`c.fsd`» с одним базовым регистром, а источники — заведомо 1,
   аргумент `line_dir` и аргумент `buff_count`. Слово `Water_Mark_Value` пишется обычной `c.sw` по
   смещению 4. Значит, это побайтовые записи по смещениям 0, 1, 2: **`c.sb`**.
3. Сравнение битов трёх кодировок даёт раскладку смещения: смещение 1 — бит 12, смещение 2 — бит 5.
4. В `UHSIF_IRQHandler` четыре «`c.fld`» отличаются только битами 10 и 11. Обработчик перебирает
   четыре канала, `Thread_Dir` лежит по смещениям 1, 9, 17, 25 — значит, бит 10 = 8, бит 11 = 16.
   Это **`c.lbu`**.
5. Проверка на остальных местах: `c.lbu a5, 0(a2)` в `UHSIF_Cfg` читает байтовую таблицу
   `UhsifWavedataPosition_*` — ровно то место, где декомпилятор Ghidra запутался в индексе.

Итог, с которым сходятся все 14 мест:

| Инструкция | Квадрант | funct3 | Поля |
|---|---|---|---|
| `c.lbu rd', uimm(rs1')` | 00 | 001 | uimm[4:0] = {b11, b10, b6, b5, b12}, rs1' = b[9:7], rd' = b[4:2] |
| `c.sb rs2', uimm(rs1')` | 00 | 101 | то же, rs2' = b[4:2] |

Других опкодов `xw2p2` в библиотеке нет.

## 5. Ловушки и как их обходить

- **Слепое пятно инструментов.** Отказ «unimplemented instruction» — не признак шифрования или
  обфускации. Сначала проверить, стандартное ли расширение (Zb*), потом искать собственное.
- **Собственные сжатые опкоды занимают кодировки FP.** На ядре без FPU всякая `c.fld/c.fsd/c.flw`
  в листинге — повод присмотреться.
- **millicode `-msave-restore`** ломает восстановление аргументов в декомпиляторе. Аргументы смотреть
  по дизассемблеру: до вызова `__riscv_save_N` они лежат в `a0..a7`, после — разложены по `s*`.
- **Цикл «копировать таблицу в периферию»** декомпилятор показывает запутанно (индекс принят за
  указатель). Такие места проще понять по трассе эмуляции, чем по C.

## 6. Spike: прогон функций в эмуляторе

Статика даёт структуру, но точную последовательность записей в регистры — с учётом аргументов,
режимов и порядка — надёжнее снять динамически. Функции библиотеки прогоняются в Unicorn
([`spike.py`](../tools/uhsif-re/spike.py)). Свой эмулятор не пишется: Unicorn исполняет почти
весь код, а хуки закрывают только то, чего он не знает.

Устройство:

- в память грузится плоский ELF из шага 2: код, данные, стек в RAM;
- **внешние функции.** В каждый адрес-ловушку кладётся настоящая инструкция возврата:
  `jalr x0, 0(ra)`, а для `__riscv_save_N` — `jalr x0, 0(t0)`, потому что millicode вызывается
  через `jal t0`. Хук на этом адресе срабатывает до инструкции и делает работу функции:
  `memcpy/memset` выполняет, `GPIO_Init` и `RCC_*` журналирует с разбором аргументов
  (`GPIO_InitTypeDef` из публичного заголовка), `__riscv_save/restore_N` сохраняет и восстанавливает
  `ra, s0…` по соглашению libgcc;
- **неизвестные инструкции.** 30 мест Zb* и XW из шага 4 находятся автоматически по кодировке. В
  памяти они заменяются NOP того же размера, а хук на их адресе выполняет настоящую семантику над
  регистрами. PC из хука не трогается вообще;
- **`mret`** в обработчике прерывания заменяется на `ret`, и обработчик вызывается как обычная функция;
- **периферия** (`0x40000000…`, PFIC `0xE000E000…`) отображена как обычная память с хуком на
  каждое чтение и запись. Память хранит записанное, поэтому чтение-модификация-запись ведёт себя
  естественно. Нужные «аппаратные» значения (флаги прерываний, номер сокета, принятая длина)
  выставляются перед вызовом. Журнал: «R/W, адрес, значение, функция+смещение»;
- после вызовов выгружаются DMA-дескрипторы из `.bss` — это RAM, хук периферии их не видит.

Сценарий повторяет пример WCH: `UHSIF_GPIO_Init(SLAVE_FPGA, PINREMAP2, CLKREMAP1, 0, BIT32)` →
`UHSIF_Cfg()` → `UHSIF_Line_Cfg` для двух каналов → `UHSIF_Start(ENABLE)` → `UHSIF_Trans_Cfg`.
Затем обработчик прерывания вызывается для каждого канала, двух буферов и каждого бита состояния.
Тот же сценарий прогоняется в режимах Slave_SOC и Master, и `diff` трасс показывает, какие биты
отвечают за режим. Отдельный короткий прогон с разной шириной шины нашёл поле `width_bit`.

**Перебор параметров.** Раз функция исполняется за миллисекунды, её можно прогнать на всей сетке
аргументов. [`pinmap.py`](../tools/uhsif-re/pinmap.py) вызывает `UHSIF_GPIO_Init` для всех
3 × 4 × 4 сочетаний «ремап выводов × ремап такта × ширина» и сводит вызовы `GPIO_Init` в таблицу.
Затем таблица сверяется с двумя независимыми документами: «UHSIF_PORTn → вывод» из даташита и
«сигнал → UHSIF_PORTn» из руководства. Все три источника сошлись, кроме одного места (AF#
настроен как вход). Такое расхождение — первое, что надо проверить на железе.

Всё воспроизводится одной командой [`run.sh`](../tools/uhsif-re/run.sh): скачать, распаковать,
перелинковать, дизассемблировать, снять три трассы и, если задан `$GHIDRA`, декомпилировать.

### Грабли, на которые наступили

- **Смена PC из хука в RISC-V-порте Unicorn ненадёжна.** Первый вариант (хук делает работу и
  переставляет PC) падал с `UC_ERR_EXCEPTION` на первом же вызове заглушки. Решение — не трогать PC:
  настоящий `jalr` в заглушке, NOP вместо неизвестной инструкции.
- **`mret` переводит ядро в U-режим.** MPP после первого `mret` равен 0, и второй вызов
  обработчика падает на привилегированной инструкции. Отсюда замена на `ret`.
- **Коды доступа Unicorn:** `UC_MEM_READ = 16`, `UC_MEM_WRITE = 17`. Перепутаешь — получишь
  правдоподобный, но неверный журнал (записи с «старыми» значениями). Брать константы из модуля.
- **`pyelftools` отдаёт тип секции как `SHT_PROGBITS`**, а не `PROGBITS`. При ошибке память
  остаётся пустой, и эмулятор молча исполняет нули.
- **Побочные эффекты API.** `UHSIF_Reg_Cfg(mode, 5, …)` пишет прямо в живой регистр флагов
  прерываний, который обработчик читает первым. Порядок вызовов в сценарии важен.
- **Индексы таблиц надо проверять, а не угадывать.** Дескрипторы оказались проиндексированы
  `line·8 + buf`, а регистры сокетов — `buf·4 + line`. Первая выгрузка смотрела не туда.
- **Скрипт рядом с данными.** Свой `dis.py` в рабочем каталоге перекрыл стандартный модуль `dis`, и
  pyelftools упал на импорте. Скрипты держать отдельно от данных, Python запускать с `-I`.

Журнал — готовая спецификация для своего драйвера: какие регистры, в каком порядке, какими
значениями. Сводка — в [ch32h417-uhsif.md](ch32h417-uhsif.md#что-делает-библиотека-по-трассам-spike).

## 7. Проверка на железе

Эмуляция показывает, что библиотека пишет, но не то, что значат биты. Последний шаг — на плате:
свой драйвер, построенный по журналу, против `libUHSIF.a`; PRBS с ПЛИС; SLogic16U3 на шине; дамп
регистров `0x40038000..` после инициализации обоими способами должен совпасть.

## Что обобщается на другие библиотеки

1. Не урезан ли объект: символы экономят больше всего времени.
2. Перелинковать в плоский образ с ловушками на внешних символах — и статика, и эмуляция работают
   с одним файлом.
3. Сверять два независимых дизассемблера. Расхождения и есть интересные места.
4. Неизвестные опкоды выводить из данных: известная раскладка структуры из публичного заголовка —
   лучший «оракул».
5. Динамику снимать в готовом эмуляторе с журналом MMIO, а неподдержанные инструкции заменять NOP и
   исполнять в хуке поадресно. Свой полный эмулятор писать не нужно.
6. Дешёвый прогон в эмуляторе позволяет перебрать аргументы целиком и сверить результат с
   документацией. Расхождения указывают на ошибки либо в библиотеке, либо в документах.
7. Константы, которые компилятор вписал прямо в код, искать в «мёртвых» таблицах: здесь
   `UhsifTransition_*` не имеют ни одной ссылки, но совпадают с тем, что пишется в `UHSIF+0x180…`.

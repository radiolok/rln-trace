# JTAG цели: журнал

Свой движок отладки для зонда (шаг 6 [стенда](bench.md#отладка-swdjtag)). Цель — STM32F4-Discovery, зонд
пока на Tang Nano 9K; потом тот же движок переедет в SLogic16U3 с каналом команд по USB 3.0. Блоки
**«Для статьи»** — находки для рассказа.

## Шаг 1: OpenOCD через remote_bitbang и UART (2026-11-08)

**Что собрано.** Tang Nano 9K, образ [`top_jtag`](../gw/boards/tangnano9k/README.md#jtag-зонд-для-stm32f4-discovery-top_jtag).
Цепочка: OpenOCD (`remote_bitbang`) → TCP 3335 → [`sw/rbb/rbb_bridge.py`](../sw/rbb/rbb_bridge.py) → UART BL702 (канал B,
`/dev/ttyUSB1`) → [`uart_rx`](../gw/cores/uart_rx.sv) → [`rbb_jtag`](../gw/cores/rbb_jtag.sv) → выводы J5 → PA13/PA14/PA15/PB3/PB4/NRST.
Протокол — один байт ASCII на команду: `0`–`7` = {TCK, TMS, TDI}, `R` → `0`/`1`, `r`–`u` = {TRST, SRST}.
Ответы TDO копятся в очереди на 16 бит, так что `R` подряд не тормозит приём.

**Почему так.** Канал наружу у 9K — только UART BL702, а драйвер OpenOCD для протокола «байт на такт» уже
есть. Ни строчки C на ПК, проверять можно сразу настоящим OpenOCD. Движок здесь — просто регистр выводов.
Сдвиговое ядро, CMSIS-DAP и SWD — следующие шаги.

**Проверка.**
- Verilator: `make -C gw test-rbb` — все команды, 64 чтения TDO вперемешку с тактами. Отправитель на 3 %
  быстрее приёмника, очередь ответов при этом растёт.
- UART без потерь: 4000 `R` подряд — 4000 ответов. Тот же поток байт, что OpenOCD шлёт при `init`
  (снят заглушкой-сервером, 3273 байта, 1007 `R`), прямо в порт — 1007 ответов.
- OpenOCD: найдены обе TAP — `0x4ba00477` (JTAG-DP Cortex-M4) и `0x06413041` (граничное сканирование F407).
  `reset halt`, PC = 0x080002c0, UID `002a0019 32314714 31383435`, DBGMCU_IDCODE `0x10016413` (rev Z),
  `flash probe` — 1024 КиБ. Вся сессия — 1,5 с.

| UART | Чтение 16 КиБ ОЗУ (`dump_image`) | Скорость | `verify_image` (CRC на цели) |
|---|---|---|---|
| 1 Мбод (DIV 27) | 8,9 с | 1,8 КБ/с | 0,51 с |
| 3 Мбод (DIV 9) | 4,4 с | 3,7 КБ/с | 0,27 с |

Втрое быстрее UART — только вдвое быстрее чтение: остальное съедает задержка USB 1.1 у BL702 на каждом
обмене OpenOCD «отправил — жду TDO».

**Грабли.**
- **Первое открытие `/dev/ttyUSB1` после загрузки ПЛИС иногда молчит** — BL702 будто не берёт скорость.
  Повторное открытие работает. Мост теперь при старте шлёт `R` и переоткрывает порт, пока не придёт ответ.
  Самое первое зависание OpenOCD на `DR scan interrogation` было именно этим: команды уходили, ответы — нет.
- `ttyUSB0` — канал A BL702 (JTAG самой ПЛИС), на запись отвечает эхом `\xfa<байт>`. Не путать.
- `stm32f4x.cfg` меняет `adapter speed` в событиях reset-start и reset-init, а у `remote_bitbang` скорости
  нет — `reset halt` падает с «Translation from khz to adapter speed not implemented». В
  [`stm32f4-rbb.cfg`](../sw/rbb/stm32f4-rbb.cfg) те же события переопределены без смены скорости.
- После `resume` — сотня `DAP transaction stalled (WAIT)`: прошивка трассы ставит RCC_CFGR = 0x94f0
  (HCLK = HSI / 512 = 31 кГц), и доступы AP ждут ядро. Тот же эффект, что у ST-LINK; `halt` всё равно
  проходит. Подключение — под сбросом (`connect_assert_srst`).

**Для статьи.** Отладчик за вечер: 200 LUT, UART и драйвер OpenOCD, который был там всегда. Медленно —
3,7 КБ/с, но это настоящая сессия: IDCODE, halt, регистры, флеш. Узкое место — задержка обмена через USB,
а не JTAG: каждое чтение TDO — круг до ПК и обратно. Отсюда и следующий шаг — сдвиг в ПЛИС целыми словами.

## Что дальше

1. Сдвиговое ядро: TMS/TDI векторами, TCK из делителя, TDO назад словами — меньше обменов на бит.
2. SWD на тех же выводах (`remote_bitbang` умеет `O`/`o`/`c`/`d`–`g`) — быстрая проверка до своего протокола.
3. Канал команд в SLogic16U3 по USB 3.0, протокол CMSIS-DAP v2.

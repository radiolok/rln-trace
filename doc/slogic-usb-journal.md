# SLogic16U3: журнал своего USB

Продолжение [трассы STM32](slogic-trace-journal.md) и [BE-U1000](beu1000-trace-journal.md): до сих пор
трасса уходила с SLogic16U3 только через JTAG (буфер 8 Кслов, потом чтение). Цель — непрерывный поток на
ПК по USB. Порядок выбран такой: сначала USB2 HS на готовых IP Gowin (около 35–40 МБ/с, канал команд
и отладки), затем USB3 на SerDes. Блоки **«Для статьи»** — повороты и находки для рассказа.

Источники:

- Gowin IPUG781 — USB 2.0 SoftPHY (схема подключения для Arora V, типы выводов): `doc/gowin/IPUG781E-usb2-softphy.pdf`
  (в git не кладётся, скачан с cdn.gowinsemi.com.cn/IPUG781E.pdf);
- [gowinsemi/USB2Peripheral](https://github.com/gowinsemi/USB2Peripheral) — справочный проект Gowin на тех же IP
  (верхний модуль, подключение контроллера к PHY; дескрипторы зашифрованы);
- [usb_serial](https://jorisvr.nl/article/usb-serial) Й. ван Рантвейка (VHDL, 2013) — из него вырос USB 2.0 Device
  Controller Gowin: те же комментарии к портам, тот же интерфейс ПЗУ дескрипторов;
- DS981 (GW5AT): пределы PLL — PFD 19–81,25 МГц, VCO 650–1300 МГц; REFCLK SerDes 20–800 МГц;
- [ciniml/fpga_samples](https://github.com/ciniml/fpga_samples), `eda/slogic16u3_usb2` (К. Ида, BSL-1.0) — USB2 HS
  на этом же SLogic16U3 со своим PHY: какая пара dx, D14 = разрешение генератора, настройка SerDes, от которой
  взят такт (`tools/slogic/usb2/serdes/` — оттуда);
- [sipeed/TangMega-138KPro-example](https://github.com/sipeed/TangMega-138KPro-example), `usb2_soft/usb_cy_streamer` —
  Gowin SoftPHY на Arora V (GW5AST-138): fclk 960 МГц, TX Delay 1, RX Normal;
- [Daisho](https://github.com/enjoy-digital/daisho), `core/usb2` (Marshall H., BSD-2) — открытый USB2 device
  поверх ULPI: пакетный и протокольный уровни взяты в `tools/slogic/usb2/daisho/`;
- USB 2.0, 7.1.7.5 (сброс и согласование HS), UTMI 1.05 — чирп через OpMode 2 и LineState.

## Итог (2026-10-25)

| Что | Состояние |
|---|---|
| Выводы USB2 | Gowin SoftPHY, Single LVDS: dx = K3/K2, терминаторы = P2/P1, подтяжка C14, D14 — разрешение генератора 125 МГц |
| Точный такт | генератор 125 МГц → REFCLK0 SerDes Q0 → линия 0 на 1,25 Гбит/с → tx_pcs_clkout 125 МГц → 2 PLL → 960/60 МГц; +42 ppm к SOF хоста |
| USB2 FS | **работает**: перечисление, bulk IN 1,10 МБ/с без единого разрыва счётчика, bulk OUT |
| USB2 HS | **работает**: 480M, bulk IN **25,45 МБ/с** (WSL через usbipd) 30 с без разрывов, `tx_failed` 0; bulk OUT; любые наполнения пакетов |
| Свой стек USB2 | **работает**: ядро Daisho + свой слой UTMI (`usb2d.v`), чирп по KJ хоста, HS, bulk IN **23,8 МБ/с** 30 с без разрывов, bulk OUT 1 МиБ; без IP Gowin, кроме PHY |
| Сборка | целиком из командной строки, без GUI Gowin: `tools/slogic/usb2/build.sh` |

```sh
export RLN_FPGA_USB=1-2                     # наша FT2232H (JTAG ПЛИС), см. журнал BE-U1000

python3 tools/slogic/usb2/usb2.py           # состояние, счётчики, dbg контроллера
python3 tools/slogic/usb2/usb2.py log -n 200   # журнал пакетов (SOF не пишется)
"/mnt/c/Program Files/usbipd-win/usbipd.exe" attach --wsl --hardware-id 1209:0001
python3 tools/slogic/usb2/usb2stream.py --sec 5    # скорость и непрерывность EP1 IN
```

Свой стек (Daisho):

```sh
sh tools/slogic/usb2/build.sh d             # IP PHY/PLL из первой сборки → usb2d.fs
sh tools/slogic/usb2/sim/run.sh             # симуляция ядра с моделью UTMI и хоста (и -DFS)
$O/openFPGALoader -c ft2232 --busdev-num 1:$(cat /sys/bus/usb/devices/1-2/devnum) -m tools/slogic/usb2/usb2d.fs
python3 tools/slogic/usb2/usb2d.py          # состояние шины, счётчики, ошибки CRC
python3 tools/slogic/usb2/usb2d.py log -n 60   # журнал: сброс, чирп, KJ хоста, пакеты
python3 tools/slogic/usb2/usb2d.py --off 1  # отключиться от шины (--off 0 — подключиться)
```

Привязка `usbipd bind --hardware-id 1209:0001` (администратор) и правило udev для `1209:0001`
уже сделаны. VID:PID — тестовый `1209:0001` pid.codes, только для своих опытов.

Тестовые наполнения EP1 IN — для проверки передачи HS: `usb2.py --pat 1|2|3` (0x00 / 0xFF / 0x7E вместо
счётчика), `--len N` — длина пакета в байтах; `--pat 0 --len 0` — обратно.

## 2026-10-25. Где D+ и D−

Схемы прибора нет, BSDL Gowin не публикует. Зацепка из [прозвонки](slogic-pinmap-journal.md): образ
с подтяжкой всех выводов вверх вызывал на хосте «0000:0002», а пустой — нет. Значит, к D+ идёт вывод ПЛИС.

Образ `uprobe`: 22 свободных GPIO (все, кроме CH0–CH15, JTAG, флеш, RECONFIG_N, DONE, READY, MODE),
каждый по команде ER2 — вход, 0 или 1 (DRIVE=4). По очереди ведём каждый и смотрим, кто идёт следом.

| Цепь | Выводы | Что |
|---|---|---|
| D+ | P2, H3 — напрямую; K3, C14 — каждый через свой резистор | |
| D− | P1, M2 — напрямую; K2 — через резистор | |
| опорное | H2 + M1 | ~0,13 В (1,8 кОм / 75 Ом) |
| — | D14 E14 G14 одиночные; C13 D13 E13 F13 F14 H13 H14 J12 M8 снаружи в 1; G13 — 1,26 МГц | |

Разделили D+ и D− пары LVDS: K3/K2 — пара IOL26 A/B, P2/P1 — IOL35 A/B, A всегда в первой цепи.
Проверка на хосте: C14 = 1 или K2 = 1 → Windows видит подключение; все Z → устройства нет.

Это ровно Single LVDS из IPUG781 (Arora V):

| Порт SoftPHY | Вывод | Тип (IPUG781) |
|---|---|---|
| `usb_dxp_io`/`usb_dxn_io` | P2/P1 (банк 3), 36 Ом — **неверно, см. HS ниже: dx = K3/K2** | LVCMOS33D, DRIVE=8 |
| `usb_rxdp_i` | H3, N = H2 | LVDS25 |
| `usb_rxdn_i` | M2, N = M1 | LVDS25 |
| `usb_term_dp_io`/`dn` | K3/K2 (банк 4), ~100 Ом | LVCMOS33 |
| `usb_pullup_en_o` | C14 (банк 1), 1,5 кОм | LVCMOS33 |

`rxdp`/`rxdn` — LVDS-приёмники «линия против опорного»: их N-выводы и есть общая цепь H2+M1.

**Для статьи: вывод, который перезагружает прибор.** Первый проход перебора оборвался: после «D13 = 0»
пропал образ, регистр состояния Gowin показал DONE и флаг зашифрованного образа — ПЛИС сама загрузила
заводское приложение из флеш. D13, видимо, разведён на RECONFIG_N. Второй проход оборвался на шаге
*после* «D13 = 1»: утилита отпускала вывод в порядке «уровень 0, потом выход выключить», и на долю
микросекунды D13 становился нулём. Теперь порядок: все выводы в Z → уровень → разрешение, а в 0 ведутся
только те выводы, что снаружи и так в 0.

## 2026-10-25. Такт: генератор, которого нет ни на одном выводе

USB HS требует ±500 ppm, OSCB ПЛИС для этого не годится. На всех GPIO нашёлся только такт 1,26 МГц на G13 —
похоже на DC-DC (TMI7003). Пользователь нашёл на плате генератор 125 МГц, выводы уходят во внутренние слои.
Раз его нет на GPIO, он на REFCLK SerDes — 125 МГц × 40 = 5 Гбит/с USB3.

Образ `sdprobe`: квад Q0 из `GowinModGen -type SERDES` (протокол USB3_0_PHY, своя заглушка вместо
протокольной части), CSR — из toml через `serdes_toml_to_csr_15k.exe`, в сборку — `set_csr`. Наружу:
детекторы REFCLK, CMU_OK, такты квада с частотомерами (счёт в своём домене, код Грея).

| Сигнал | Значение |
|---|---|
| CMU1_OK (QPLL1, 5 ГГц от 125 МГц) | **1** — захват |
| REFCLK_DET CM2, CM3 | 1 (CM0, CM1 — 0) |
| CM1_LIFE_CLK, CMU1_CLK, QUAD_CLK_RX | ~61,8 МГц по OSCB. Принял за 62,5 при «OSCB на 1 % быстрее» — **ошибка**: по SOF хоста эти такты на 1,05 % медленнее 62,5, с генератором они не связаны (см. HS ниже) |
| PCS линии 0 | ~31 МГц (линия не в рабочем режиме, не нужна) |

480 МГц из 62,5 одним PLL целочисленно не получить (7,68 = 192/25, PFD ≥ 19 МГц). Два PLLA каскадом:
62,5 × 16 / 25 = 40 МГц, 40 × 24 = 960 МГц → /2 = 480 (fclk SoftPHY), /16 = 60 МГц. На железе 60 МГц
против 62,5 — ровно 60,0000.

**Для статьи: toml без документации.** Утилита toml→csr для 15K — Python, собранный Nuitka; формата нет,
пример есть только для 138K. Ключи восстановлены по `KeyError`: скрипт сам добавлял недостающий ключ в
`[q0]`, потом в линии, потом наверх, и так 30 раз (`mclk_freq = "50M"` — строкой; `rx_seperated_width_mode`
— числом). Итог — [`sdprobe/serdes.toml`](../tools/slogic/sdprobe/serdes.toml).

**Для статьи: IP без GUI.** Генератор софт-IP Gowin живёт только в GUI, но всё, что он делает, —
пишет `*_name.v`/`*_define.v` и синтезирует зашифрованное тело. Шаблоны дефайнов — строками в DLL
(`strings`): типы точек Bulk = 0, Iso = 1, Int = 2; у SoftPHY `TX_DELAY_n_BIT`, `D_LVDS`, `V_120`,
`GW5AT`. Оба IP используют макрос `module_name`, поэтому каждый синтезируется отдельным проектом
(`-disable_io_insertion 1`) в нетлист, а нетлисты подключаются к основному. PLL и SerDes —
`GowinModGen -do x.mod`.

## 2026-10-25. Первое перечисление: читаем USB изнутри

Первый образ: PLL захвачены, HS = 1, хост 4 раза сбрасывал шину, принято 21 SETUP — и «сбой запроса
дескриптора». Чтобы не гадать, в образ встроен журнал пакетов на уровне UTMI: на каждый принятый и
переданный пакет — направление, PID, второй байт, длина, rxerror, метка 60 МГц; 4К пакетов в BSRAM,
чтение через JTAG.

```
← SETUP адрес 0 → DATA0 80 06 …     → ACK       (GET_DESCRIPTOR)
← IN адрес 0                         → NAK, NAK, NAK …
```

**Для статьи: cork, который запирает и нулевую точку.** `txcork` у контроллера Gowin описан как «не
отдавать неполный пакет» для потоковых точек, и я держал его в 1 для всех точек, кроме EP1. Оказалось,
он действует и на EP0 — ответы на стандартные запросы ждали, пока приложение «разрешит». В справочном
проекте Gowin для EP0 cork снят. После исправления:

```
← SETUP → DATA0 80 …  → ACK
← IN    → DATA1 12 01 00 02 … (21 байт: PID + 18 + CRC)  ← ACK
← OUT ZLP → ACK
```

Интерфейс ПЗУ дескрипторов — как у usb_serial: адрес контроллер защёлкивает сам, байт нужен в следующем
такте — ПЗУ комбинационное; `desc_oscfg_addr` указывает на один байт 0x07, им подменяется тип
дескриптора при запросе other_speed_configuration.

## 2026-10-25. FS работает, HS — нет

Без `HSSUPPORT` (нет chirp) устройство перечисляется полностью: Windows — `1209:0001 SLogic16U3 trace`
со строками; в WSL (usbipd, 12M) `usb2stream.py`: 5,57 МБ за 5 с, **1,10 МБ/с** (потолок FS ~1,2),
**0 разрывов** счётчика; EP1 OUT принял 4096 байт; 87040 IN-транзакций, у каждой txpktfin.

С `HSSUPPORT` после сброса идёт chirp (в журнале — передача на 1023 байта), HS = 1, и приём ломается:
каждые 124 мкс (микрокадры SOF) — «пакеты» по 0–1 байта с PID F1–FD, то есть `1111xxxx`. В NRZI
единица — отсутствие перехода: детектор активности (rxdp/rxdn против опорного) срабатывает, а со входа
данных после нескольких бит переходов нет.

| Опыт | Результат |
|---|---|
| RX Normal | обрывки 0–1 байт, PID 1111xxxx |
| RX Advance (`V_120`, рекомендован для Arora V) | всплески rxactive без единого байта |
| TX Delay 1, 2 (× Normal/Advance) | то же |
| терминаторы DRIVE=4 | в HS тишина |
| терминаторы DRIVE=16, dxp/dxn DRIVE=12 | всплески rxactive без байтов |
| терминаторы IP уведены на свободные E14/D14 | хост сбрасывает 229 раз, ни одного SOF |

Заводской DFU Sipeed (по всей видимости, на том же SoftPHY) на этой плате — **480M** (`lsusb -t` через
usbipd). Железо HS держит; ошибка — в моих настройках.

## 2026-10-25. HS работает: три ошибки разом

Ошибок оказалось три, и каждая маскировала следующую. Помогли два чужих проекта: ciniml
(`eda/slogic16u3_usb2`) поднял HS на этом же приборе со своим PHY, а пример Sipeed для Tang Mega 138K Pro —
это Gowin SoftPHY на Arora V.

**1. Пары перепутаны.** dx — это K3/K2, терминаторы — P2/P1 (у ciniml: «в FS работает любое назначение,
в HS — только это»). Мой uprobe отличал «напрямую» от «через резистор», но какая пара передатчик, а какая
терминатор, по этому не скажешь. После перестановки — та же картина: HS-приём даёт PID F8…FD по 0–1 байту.

**2. fclk 960 МГц, а не 480.** IPUG781 пишет «fclk_i — 480 МГц», но у Sipeed на Arora V PHY получает
960 МГц (VCO 960, CLKOUT0 /1, CLKOUT1 /16 = 60), `sclk` PHY выходит 120 МГц. IDES16 на 960 МГц DDR —
4 отсчёта на бит HS; на 480 их было 2, и DRU, рассчитанный на 4, ловил SYNC, а дальше выдавал мусор.
После этого приём HS заработал полностью: SOF 8000/с, SETUP, перечисление в Windows, строки читаются.
Но bulk-пакеты по 512 байт хост не подтверждал (`tx_failed` растёт, IN повторяется).

**3. Такт квада не от генератора.** Сбой передачи зависел от данных (`--pat`/`--len`, 40 попыток на
клетку, после ошибки `clear_halt`):

| Наполнение | 4 | 8 | 16 | 32 | 64 | 128 | 512 байт |
|---|---|---|---|---|---|---|---|
| 0x00 (переход на каждом бите) | 0 | 0 | 0 | 2 | 0 | 4 | 40 |
| 0xFF (вставка бита каждые 6) | 0 | 39 | 40 | 40 | 40 | 40 | 40 |
| 0x7E (шесть единиц в каждом байте) | 0 | 4 | 32 | 40 | 40 | 40 | 40 |

Длинные участки без переходов и длинные пакеты — так ведёт себя приёмник хоста, когда частота передатчика
далеко за допуском. Замер по SOF (журнал UTMI с записью SOF: номера кадров подряд, время по 60 МГц)
показал 59 371 такт на 1 мс хоста вместо 60 000 — **−10 483 ppm**, при допуске HS ±500 ppm. FS (±2500 ppm
по спецификации) и приём HS (DRU подстраивается) это терпели. Источником опоры был `CM1_LIFE_CLK`
квада; `CMU1_CLK` и `QUAD_CLK_RX` дали то же самое. С тактом от линии 0 в режиме Customized PHY
(REFCLK0 → CPLL0, 1,25 Гбит/с, `tx_pcs_clkout` 125 МГц — настройка SerDes ciniml) и цепочкой
125 → 60 (VCO 1200) → 960/60 (VCO 960): **+42 ppm**, все наполнения и длины — 0 сбоев из 40.

| Проверка (WSL, usbipd) | Результат |
|---|---|
| `lsusb -t` | 480M, bulk 512 байт |
| дескрипторы 10–34 байта, 1500 запросов | 0 сбоев |
| EP1 IN, 30 с | 763,6 МБ, **25,45 МБ/с**, 0 разрывов счётчика, `tx_failed` 0 |
| EP1 OUT | 65 536 байт приняты |

25 МБ/с — скорее предел usbipd, а не прибора: каждая IN-транзакция с txpktfin, NAK нет.

Опыты, которые не помогли (ради полноты): TX Delay 0/1/2, RX Normal/Advance, LVPECL33E и DRIVE 4/12 на dx,
сдвиг фазы clk60 на 2/4/6 тактов VCO (hold-нарушения синхронизаторов FIFO PHY ушли, сбои — нет), PHY
из старой Gowin EDA 1.9.10 (нетлист из примера Sipeed). Терминаторы при передаче HS PHY держит в 0
(подсмотрено, выведя наружу сети IOBUF из незашифрованной верхушки нетлиста PHY).

**Для статьи: генератор, которого не было.** В sdprobe всё сходилось: QPLL1 «захвачен», в логике
«62,5 МГц», отношение PLL ровно 60,0000. Единственное расхождение — OSCB показывал 61,8, и я списал его на
неточный внутренний генератор ПЛИС. А неточным был как раз «точный» такт. Отношения двух тактов внутри
ПЛИС ничего не говорят о том, какой из них верный, — нужен внешний эталон, и он был под рукой всё время:
хост шлёт SOF ровно каждые 125 мкс.

**Для статьи: «480 МГц» в документации.** IPUG781 для всех семейств пишет fclk_i 480 МГц. Для Arora V это
не так: PHY там считает отсчёты IDES16 по 4 на бит и ждёт 960. Узнать это можно только из чужого проекта —
пример Sipeed, где PLL прямо называется `fclk_960M`.

## 2026-10-25. Свой стек: Daisho поверх UTMI

Device Controller Gowin — закрытый нетлист с комбинационным ПЗУ дескрипторов и без EP0 для своих
запросов. Замена — USB2-часть Daisho: пакетный уровень (`usb2_packet`), EP0 со стандартными запросами,
двойные буферы bulk по 512 байт. Она написана под внешний PHY с ULPI. SoftPHY Gowin умеет и ULPI, но гонять
ULPI внутри ПЛИС незачем: я заменил `usb2_ulpi.v` своим `usb2_utmi.v` с тем же интерфейсом к пакетному уровню.

Передача. Пакетный уровень рассчитан на ULPI: первый байт — TX_CMD `{4'h4, PID}`, байты уходят по `nxt`,
`stp` — в такте после последнего принятого байта. На UTMI это ложится почти один к одному: фронт `latch` →
PID `{~P, P}` с `txvalid`; `nxt` = `txready`; `txvalid` снимается комбинационно по регистру `stp`,
так что лишнего байта PHY не видит. Приём: `act` = `rxactive`, `latch` = `rxactive & rxvalid`.

Шина. У Daisho согласование HS вслепую: чирп K 2 мс и сразу HS, KJ хоста не проверяется; сброс шины
адрес не обнуляет. Свой автомат: SE0 ≥ 4 мкс в FS → сброс (пакетный и протокольный уровни в сбросе) →
чирп K 2 мс (XcvrSelect HS, TermSelect FS, OpMode 2, данные 00h) → K-J-K-J-K-J хоста по LineState,
каждый ≥ 2,5 мкс → HS. Нет чирпов 1,5 мс → FS. В HS 3 мс без активности → FS, через 100 мкс SE0 —
сброс, J — приостановка, K — выход из неё в прежнюю скорость. Будет ли LineState SoftPHY показывать
чирпы хоста при XcvrSelect = HS, по документации понять нельзя (PHY зашифрован). Поэтому в журнал
пишутся события автомата: смены состояния и LineState вне FS/HS. Оказалось — показывает:

```
    9 +      4.05 мкс  ── CHIRP_K    linestate SE0 opmode 2 xcvr 0 term 1 чирпов 0
   14 +   1999.87 мкс  ── CHIRP_WAIT linestate K   opmode 2 xcvr 0 term 1 чирпов 0
   16 +     25.47 мкс  ── CHIRP_WAIT linestate K   opmode 2 xcvr 0 term 1 чирпов 0
   17 +     48.85 мкс  ── CHIRP_WAIT linestate J   opmode 2 xcvr 0 term 1 чирпов 1
   ...
   21 +     48.88 мкс  ── CHIRP_WAIT linestate J   opmode 2 xcvr 0 term 1 чирпов 5
   22 +      2.55 мкс  ── HS         linestate J   opmode 0 xcvr 0 term 0 чирпов 6
   23 +  85282.63 мкс  ← хост SETUP  адрес 0        3 байт
```

Хост отвечает чирпом через 25 мкс, чирпы по 49 мкс. Перечисление под Windows прошло с первого раза,
без единого повтора; ACK уходит через 0,17 мкс после конца пакета хоста, DATA — через 0,3–0,8 мкс.

До железа — симуляция (`sim/tb_usb2d.v`, iverilog): модель UTMI и хоста с CRC5/CRC16, сброс, чирп, KJ,
GET_DESCRIPTOR, SET_ADDRESS (старый адрес больше не отвечает), строка, GET_STATUS, CLEAR_FEATURE,
SET_CONFIGURATION, 6 IN по EP1 (третий без ACK — повтор того же пакета), PING и OUT по EP2, сброс после
3 мс тишины; HS и FS (байт раз в 40 тактов). Она нашла три ошибки Daisho, которых нет в FPGA с
нулевой инициализацией регистров, и ложный чирп при подключении (SE0 до подъёма линии подтяжкой → OFF
идёт через FSRST, ждать J). В Gowin ядро собралось после переноса объявлений до использования; логика
25 %, BSRAM 55 %; нарушения тайминга — те же, что у сборки с контроллером Gowin (частотомеры, сброс PHY).

давал 23,8–24,6). Предел по-прежнему, похоже, usbip.

**Для статьи: ядро на чужой PHY.** Пакетный уровень Daisho знает про ULPI ровно три вещи: первый
байт — команда с PID, байты идут по `nxt`, конец — `stp` следующим тактом. Заменить ULPI на UTMI —
это 30 строк, а не новое ядро. Остальной слой ULPI — чирп и сброс — пришлось писать заново, и это оказалась
та часть, где у оригинала были упрощения: HS вслепую, адрес, переживающий сброс шины.

## Открытые вопросы и что дальше

1. Скорость HS без usbipd: замер под Windows (WinUSB) или на Linux-машине, чтобы отделить предел
   прибора от предела usbip.
2. Поток трассы: FIFO на BSRAM между приёмником (tracela) и EP1 IN, флаг переполнения, отбрасывание простоя.
3. Команды по EP0 (vendor) или EP1 OUT вместо JTAG.
4. ~~Переход на USB2-ядро Daisho~~ — сделан (`usb2d.v`). Дальше на нём: команды vendor-запросами
   EP0 (есть `vend_req_*`, нужна стадия данных IN для чтения состояния) вместо JTAG.
5. USB3 на том же кваде (линия 0 сейчас занята под такт 125 МГц — для USB3 такт брать с её PCS-тактов): PIPE от USB3_0_PHY Gowin + стек [Daisho](https://github.com/enjoy-digital/daisho) (Verilog, USB3 поверх
   PIPE TUSB1310A — 16 бит/250 МГц против 32 бит/125 МГц у Gowin, нужен переходник ширины; там же USB2 поверх ULPI —
   SoftPHY Gowin умеет ULPI, открытая замена Device Controller).
